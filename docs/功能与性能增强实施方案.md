#### F1. 记忆闭环接线（saveAgentMemory + extractMemoriesWithModel）

**现状**
- `agent-memory.ts:124-138` `saveAgentMemory()` 是整文件覆写、best-effort，**零生产调用**——`MEMORY.md` 只有读路径（`loadAgentMemoryPrompt` 注入子代理 system prompt），没有写路径。
- `memory-extract.ts:116-176` `extractMemoriesWithModel()` **零生产调用**；`/memory extract` 只跑启发式 `extractMemoriesHeuristic()`。
- `MemoryStore.append()`（`memory-extract.ts:223-246`）自带按 normalize 文本去重，且是 prefetch 检索的数据源（`cli.ts:219-225`）——保存进去的记忆下一轮就能被检索注入。

**改动点**
1. **新增 `MemorySave` 工具**（新文件 `src/tools/extended/memory-save.ts`，注册进 `core-tools.ts`）：
   - schema：`{ content: string, scope?: "project" | "local" }`（`user` scope 不暴露给模型）。
   - 实现走 `MemoryStore.append()`（检索闭环），并在 `context` 上读取当前主 agent 类型，同步 `saveAgentMemory()` 追加进对应 `MEMORY.md`（注入闭环；注意 saveAgentMemory 是覆写，工具层需先 `loadAgentMemoryPrompt` 读原文再拼接回写）。
   - 工具描述明确："保存值得跨会话记住的事实/偏好/教训"，鼓励模型在用户纠正它之后主动调用。
2. **会话结束自动提取**：在 TUI 会话退出路径（unmount / 退出钩子）调用 `extractMemoriesHeuristic(messages, changes)` → `MemoryStore.append()`，默认开启（零 token 成本）；模型路径 `extractMemoriesWithModel` 默认关，`CCR_AUTO_MEMORY_EXTRACT=1` 开启（退出时一次模型调用）。
3. `/memory extract` 增加 `--model` 参数走模型路径；`/memory save <text>` 子命令补上 `saveAgentMemory` 写路径。
4. **中文意图识别**（与 S1 联动）：`memory-extract.ts:46` `INTENT_RE` 增加中文前缀 `记住|以后|始终|永远|不要|必须|偏好|注意`。

**测试计划**
- 新测试 `memory-save.test.ts`：写入后 jsonl 出现新行；重复文本去重；scope 校验。
- 自动提取：伪造含 `"remember to run tests"` 行的 messages → 退出钩子后 jsonl 有对应条目；mock `callModel` 返回 JSON 数组 → 解析入库；坏 JSON → 空数组不抛。
- `/memory save` 写入与幂等。

**风险与回滚**：自动模型提取有退出时延——默认关，env 开启；全部写入 best-effort，失败不影响会话。

#### F2. CollapseStore.restore 接线（裁剪内容可恢复）

**现状**
- `context-pipeline.ts:92-110` `CollapseStore` 有完整的 `collapse`/`restore` API；Layer 2/3 裁剪时写入（`:181`、`:239`），**`restore()` 无任何生产消费者**——被裁剪的原文实际找不回，模型只能重跑工具。
- `evictionStub()`（`:30-32`）生成的占位文本不含 tool_call_id，模型无从得知用什么 key 恢复。

**改动点**
1. `evictionStub()` 签名增加 `toolCallId` 参数，stub 文本嵌入 id 与指引：`[evicted: read result (id: toolu_xxx), 8k chars — call RestoreContext with this id to recover the original]`；Layer 2 的 trimmed 标记同样附 id。
2. **新增 `RestoreContext` 工具**（`src/tools/extended/` 下新文件）：
   - schema：`{ tool_call_id: string }`。
   - 需要把 `CollapseStore` 实例挂到 `ToolContext`（`agent-loop.ts:208/258` 创建处导出引用，types.ts 加可选字段 `collapseStore?: CollapseStore`）。
   - `restore(id)` 命中 → 原文作为工具结果返回（**不回填历史**——回填会破坏 prompt-cache 前缀；模型当轮即可引用）。未命中 → 明确错误信息列出当前可恢复的 id 数量。
   - 上限保护：返回内容截断到 50k chars，超出提示分段恢复（可加 offset 参数）。
3. 工具标记 `isReadOnly: true`、`isConcurrencySafe: true`，不进 COMPACTABLE_TOOLS（恢复结果本身可再被裁剪，但 stub 指引仍可再次恢复）。

**测试计划**
- pipeline 截断后 stub 文本含 id；RestoreContext 返回与原文一致；未知 id 报错；超长截断。
- 端到端：造超预算历史 → 裁剪 → 模型视角能通过工具拿回原文。

#### F3. 后台子代理（run_in_background + job-store agent kind）

**现状**
- `job-store.ts:23` `Job.kind` 已支持 `"agent"`；`settleJob()`（`:127-149`）自带 M41 完成通知（`pushTaskNotification`），`JobOutput/JobKill/JobList` 工具按 kind 无关读取——**整套消费侧已就绪，只缺生产者**。
- `agent.ts:110-113` schema 声明 `run_in_background`、`:132` prompt 描述里也写了，但 `call()`（`:151-351`）**完全没读这个参数**——纯占位。

**改动点**
1. 把 `agent.ts` `call()` 内「建 loop → 消费事件 → 提取报告」的主体抽成内部函数 `runAgentToEnd(): Promise<{report, error?, reason}>`（前台后台共用）。
2. `call()` 开头分支：`input.run_in_background === true` 时：
   - `createJob(context.sessionId, { kind: "agent", command: description || prompt.slice(0, 80), description })`；
   - 为后台 agent 建独立 `AbortController`，链到父 `context.abortSignal`（父中止 → 子中止）；`job.kill = () => controller.abort()`；
   - 后台 Promise 跑 `runAgentToEnd()`：报告写入 `job.stdout`，`settleJob(job, "done", 0)`；异常 → `settleJob(job, "error", null)` 并把错误摘要写 `job.stderr`；
   - 立即返回 `{ content: "Background agent started (job-N). Use JobOutput (wait: true) to retrieve the report; JobKill to stop it." }`。
3. 后台 agent 计入 F4 的并发信号量（acquire 在启动时、release 在 settle 时）。
4. worktree 隔离与后台组合：后台 + `isolation: "worktree"` 允许（隔离本就是为并行准备），失败路径确保 worktree 清理。

**测试计划**
- `run_in_background: true` 立即返回且含 job id；mock agentLoop 完成后 `job_output` 取到报告、status=done；`job_kill` → status=killed 且子循环收到 abort；前台路径回归不变。

#### F4. Agent 工具防护（fork 深度 + 并发信号量）

**现状**
- `task.ts` 有 `MAX_FORK_DEPTH = 1` 与 `TASK_MAX_CONCURRENCY = 3` 信号量；`agent.ts` **两者皆无**——fork 模式拿到全部 core 工具（含 Agent 自身，`agent.ts:209`），理论上可无限递归。

**改动点**
1. `types.ts` 的 `ToolContext` 加可选 `forkDepth?: number`；`agent.ts` fork 分支的子循环 `toolContext` 传 `forkDepth: (context.forkDepth ?? 0) + 1`；`agent.ts` 开头检查 `forkDepth >= 2` 时返回错误并建议改用 `subagent_type`。
2. 并发信号量：从 `task.ts` 抽出通用 `utils/semaphore.ts`（acquire/release/tryAcquire），agent 与 task 共用两把独立实例（AGENT_MAX_CONCURRENCY 默认 3，env 可调）；前台路径 `tryAcquire` 失败立即报 "too many concurrent agents"，后台路径（F3）同样计入。

**测试计划**
- forkDepth 逐层递增、超限拒绝；并发第 4 个立即报错；release 后可再入；task/agent 信号量互不侵占。

### 第二梯队 — 浅实现补深

#### S1. 中文记忆/技能检索修复

**现状**
- `prefetch.ts:60-66` `keywords()` 用 `split(/[^a-z0-9]+/)` 分词——**所有 CJK 字符被当分隔符**，中文 query 的词集恒为空 → `rankMemories`/`rankSkills`（`:86-87`、`:102-103`）对中文会话永远返回空。记忆与技能的自动注入在中文对话里从未生效。

**改动点**
1. `keywords()` 重写为混合分词：
   - 先按 `/[a-z0-9]+|[\u4e00-\u9fff]+/g` 切段；
   - ASCII 段沿用现有规则（≥3 字符 + 英文停用词）；
   - CJK 段优先 `Intl.Segmenter("zh", { granularity: "word" })` 分词（Node ≥16 内置，esbuild 打包无碍），feature-detect 不可用时 fallback 到 **bigram**（连续两字组合）；
   - CJK 词条长度 ≥2，新增中文停用词表（的/了/是/我/你/他/和/在/有/不/这/那/请/一下/什么/怎么 等）。
2. 与 F1 的 `INTENT_RE` 中文扩展联动（同一批交付）。

**测试计划**
- 中文 query 命中含相同词的记忆/技能；中英混合文本；纯英文回归不变；空 query；Segmenter 缺失时 bigram fallback 仍命中（测试里 monkey-patch 删掉 Intl.Segmenter）。

## 二、性能提升

### 高收益

#### P1. Anthropic 适配器逐 block 发 tool_use（流中早启动）

**现状**
- `anthropic-adapter.ts:347-360` 流循环只 yield `text_delta`/`thinking`；tool_use 全部等 `stream.finalMessage()` 后枚举 yield（`:378-394`），`:360-362` 注释自述 "no partial tool input event is needed"。
- 后果：`agent-loop.ts:366-377` 的早启动 + 整个 `streaming-tool-executor.ts`（设计目的就是把工具延迟藏进模型剩余流式时间）在 Anthropic 主路径上的窗口 ≈ `finalMessage()` 到 done 之间，**接近零**。

**改动点**
1. 流循环维护 per-block 累积器：`content_block_start` 且 `block.type === "tool_use"` 时登记 `{ id, name, jsonBuf: "" }`；`input_json_delta` 追加 `partial_json`；`content_block_stop` 时 `JSON.parse(jsonBuf || "{}")`（容忍空/畸形——畸形时回退到 finalMessage 兜底）并**立即** `yield { type: "tool_use", id, name, input }`。
2. `finalMessage()` 后对已 yield 过的 tool_use 按 id 去重，只补发流中断漏掉的；thinking/redacted_thinking 仍走 finalMessage（签名只在最终消息存在）。
3. abort 语义不变（loop 已有 clear() 处理）。OpenAI 路径不动（`llm-adapter.ts:267-270` 已在 finish chunk 提前发）。

**测试计划**
- 模拟流事件序列（text 与两个 tool block 交错）→ 每个 tool_use 在其 `content_block_stop` 即产出、input 解析正确；畸形 json 容错；与 finalMessage 全量枚举结果一致（去重断言）；现有 adapter 回归全绿。

**预期收益**：Read/Grep 等安全工具与模型剩余输出并行执行，每 turn 省秒级延迟。

#### P2. 会话保存增量化（消灭 O(n²) I/O）

**现状**
- `session-memory.ts:385-448` 每次保存：`load()` 读盘解析旧文件（read-modify-write）→ `JSON.stringify(data, null, 2)` 全量消息 → temp+rename 原子写 → catalog 读写。TUI 每轮状态回调都触发保存（`cli.ts:682-691`）→ 长会话累计 O(n²) I/O 且 pretty-print 放大体积近一倍。

**改动点（两步走，第一步无格式风险先行）**
1. **第一步（纯降开销，不改格式）**：
   - 会话元数据内存缓存：`Map<sessionId, {createdAt, completed, taskState, lastTerminalReason}>`，save 后更新，消除每次 `load()` 读盘解析；
   - 去掉 `null, 2` pretty-print（体积近半）；temp+rename 原子性保留；
   - catalog 写节流：preview 未变化不重写。
2. **第二步（格式演进，version bump 单独交付）**：
   - 活跃会话消息 append 到 `<id>.events.jsonl`（每条消息一行）；主 `.json` 只在会话结束 / 每 K 条消息 / 每 N 分钟时 checkpoint 重写；
   - `load()` 三态兼容：`.json` + `.events.jsonl` 重放合并；纯 `.json`；v1 走现有 migrate 链；
   - 会话 completed 时合并 events 进 `.json` 并删除 events 文件；
   - 崩溃容错：events 尾部半行丢弃（沿用 jsonl 逐行解析的容错模式）。

**测试计划**
- 第一步：mock fs 断言同会话第二次保存不再读旧文件；序列化体积对比。
- 第二步：append + 重放后 `load()` 与全量写等价；半行容错；completed 合并删除；v1/v2 迁移回归；resume/分享/导出路径回归。

**风险**：第二步动持久化格式，影响 resume/export/share——独立批次 + 充分回归；第一步先行拿到一半收益。

#### P3. token 估算记忆化

**现状**
- `agent-loop.ts:818-824` 增量基线在合成注入（prefetch `:323`、tool summary `:330`、cheap layers 改写 `:262`）后被置 `undefined` → 退化为全量 `estimateTokens()`；`token-estimator.ts:87-122` 对每条消息跑约 10 个正则（CJK/code/结构化检测），同步阻塞事件循环。

**改动点**
1. `token-estimator.ts` 拆出并导出 `estimateMessageTokens(message)`，加模块级 `WeakMap<Message, number>` 记忆化（pipeline 层以 `{...m, content}` 新对象替换、不 mutate 原消息——已验证满足 WeakMap 前提）；`estimateTokens()` 改为逐消息求和。
2. `agent-loop.ts` 合成注入后不再作废基线：纯追加型注入（prefetch/summary/通知）改为 `usageBaseline = { promptTokens: baseline.promptTokens + estimateMessages(injected), messageCount }`；只有 cheap layers **改写**旧消息时才重置。

**测试计划**
- 同一 messages 二次估算走缓存（spy 计数验证）；被 pipeline 替换的消息重算；与原实现数值逐条对拍（快照测试）。

#### P4. 权限分类器缓存 + transient 指数退避

**现状**
- `permissions.ts:320-371` `classifyPermissionRisk()` 对每个被 regex 标记的调用发起真实模型调用（默认 4s 超时），同会话相似命令每次重问；`tool-executor.ts:311-337` 串行 await 在工具执行关键路径上。
- `error-recovery.ts:131-137` transient 重试固定 `delayMs: 2000`，无指数退避（与 429 的精细退避不对称）。

**改动点**
1. `classifyPermissionRisk` 外包会话级缓存：key = `${toolName}|${formatActionForClassifier(toolName, input)}`（该格式化函数 `:374` 现成，直接复用）；`Map` 存 `ClassifierResult`，会话期有效；**BLOCK 结果同样缓存**（重复危险命令必须一致判定）。缓存实例挂在 `PermissionClassifier` 对象的可选字段上，由 cli.ts 创建会话级实例注入。
2. `error-recovery.ts` transient 分支改为 `1000 × 2^transientRetries ± 20% jitter`，cap 30s，`onRetry` 上报真实 delay。

**测试计划**
- 相同调用第二次不触发 `callModel`（mock 计数）；不同参数不命中；BLOCK 缓存一致性；fake timers 验证两次 transient 的 delay 递增。

### 中收益

#### M1. 重试保留部分输出（续写而非重来）

**现状**
- `agent-loop.ts:532-541` 重试路径 `streamExecutor.clear()` 丢弃全部已流出文本（UI 同步丢缓冲）——长回答遇 429/超时整个 turn 重来，已产生的 output tokens 全部作废且重新计费。

**改动点（保守开关式）**
1. 新增 `CCR_RETRY_CONTINUE=1`（默认关，验证期后可转默认开）：
   - 流错误发生时，若已积累纯文本 ≥1000 字符**且本轮尚未 yield 任何 tool_use** → 把 partial 文本固化为 assistant 消息 + 追加 user nudge（"Continue exactly from where you stopped, do not repeat"）→ 重试调用；
   - 已有 tool_use 流出则维持现行为（工具副作用可能已开始，续写不安全）。
2. Anthropic 路径首版**不启用**（signed thinking 块的续写会被签名校验拒绝），只对 OpenAI 兼容路径生效。

**测试计划**
- mock 模型先流 1500 字符再抛 ETIMEDOUT → messages 含 partial+nudge、最终输出为拼接结果；tool_use 已流出 → 原路径；开关关闭回归不变。

#### M2. 工具结果去重折叠

**现状**
- `context-pipeline.ts:143-193` Layer 2 只在总字节超 100k 后才截断；同一文件 Read 两次、相同 grep 结果各占全量上下文，无去重。

**改动点**
1. pipeline 新增 Layer 1.5 `dedupeToolResults()`（沿用"超阈值才运行"原则，保持 under-threshold 字节稳定）：
   - 对 `role === "tool"` 且属于 `COMPACTABLE_TOOLS` 的结果算内容 hash（djb2 足够，无碰撞安全要求）；
   - 与更早的同 hash 结果重复时，替换为 `[duplicate of earlier tool result ${tool_call_id}]`（**首个保留全文**）；keepRecent 保护窗口内的不折叠。
2. 折叠量计入 `PipelineLayerResult.charsSaved` 与 notes。

**测试计划**
- 两条同内容结果 → 第二条折叠、第一条原样；不同内容不折叠；语义工具（Task/Skill）不折叠；未超阈值整层不运行。

#### M3. grep/glob 文件列举缓存

**现状**
- `grep.ts:253-309` 每次调用 spawn `rg --files` 全量列文件再分批搜；`glob.ts:58-72` fast-glob 每次全扫。均无缓存。

**改动点**
1. 新增 `utils/fs-cache.ts`：`listWorkspaceFiles(root)` 带 TTL（默认 10s）缓存；暴露 `invalidateWorkspace(root)`。
2. write/edit/multi_edit/bash(powershell) 落盘成功后调用 invalidate——工具自身知道自己改了 fs。
3. `grep.ts` 列举走缓存（搜索本身**不缓存**，正确性优先——方案明确此边界）；`glob.ts` 结果按 `(root, pattern)` TTL 缓存同失效逻辑。

**测试计划**
- 连续两次 grep 第二次不 spawn `--files`（spy execFile）；写文件后失效；TTL 过期重列；fallback 路径（rg 不可用）不受影响。

#### M4. checkpoint 伪 turn 膨胀与内存共享

**现状**
- `agent-loop.ts:158-161` `openTurnBoundary` 让每个合成注入（stop-hook 错误、续写 nudge、M41 通知等）都触发 `beginUserTurn` → turn 计数膨胀 + 每边界 statSync×N + 加速挤掉 100 个真实快照窗口（`checkpoint.ts:122`）。

**改动点**
1. `openTurnBoundary` 增加 `{ synthetic: true }` 选项：synthetic 边界只记时间戳、不 `beginUserTurn` 不拍快照；`agent-loop.ts` 各合成注入调用点传入。
2. 快照内容改 content-addressed：`Map<contentHash, string>` 存内容、turn 只存 hash 引用——未变文件跨 turn 共享一份。
3. rewind 候选列表只列真实 turn（synthetic 边界不出现在 `/rewind` 中）。

**测试计划**
- 注入类事件后 turn 计数/快照数不变；未修改文件跨 turn 内存中只存一份（对象计数）；rewind 列表只含真实 turn；`/rewind` 功能回归。

## 四、总体风险与原则

1. **前缀缓存是隐形契约**：所有上下文改动（M2、F2、F5、P3）必须保持 "under threshold 不动字节" 原则——pipeline 现有注释（`context-pipeline.ts:298-300`）明确此设计，任何新层都要遵守。
2. **best-effort 不变**：记忆、恢复、提取全部沿用现有 fail-open 风格，任何新机制故障不得阻塞主循环。
3. **默认值从紧**：有模型调用成本的新机制（M1 续写、F1 自动模型提取、S6 提取）默认关或 env 开启，验证期后再评估转默认。
4. **死代码处置**：接线（micro-compact）与删除（context-snip）都写明在案，避免再次出现"写了没人用"的半成品。
