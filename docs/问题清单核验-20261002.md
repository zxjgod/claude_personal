# 五组审查汇总的逐项核验

> 本页记录修复前的核验。已确认问题及条件性入口的修复状态见 [v1.6.1 审查修复](更新日志/20261002-review-remediation.md)；旧行号属于当时工作区，不应据此认定当前仍未修复。

核验日期：2026-10-02。对象：当前工作区 v1.6.0（HEAD 仍为 `f28352a`，升级内容尚在工作区，不能仅审阅 HEAD）。本轮只核验，没有修改运行时代码。

## 结论

编号 1–16 中：**12 项确认存在，3 项需要限定触发条件，1 项按报告所述未成立**。

首要纠正：**第 1 项没有复现会话级权限扩大**。`executeSingleTool()` 入口复制 context，`mergePermissionPolicies()` 生成新的对象和数组；给局部 context 赋值不会写回父会话。连续调用已证明一次 Hook allow / deny 不影响下一次调用。不能据此修复一个并不存在的“持久 policy 被改写”问题。

项目 LSP 缺少信任门、WebFetch 域名规则绕过、MCP URL 打开流程、用户记忆免审批写入及会话目标恢复问题需要处理。测试全部通过并不说明这些未覆盖的路径正确；上一轮升级确实遗漏了其中若干问题。

| 项 | 判定与准确边界 |

| manifest server 路径逃逸 | **属实**。[校验集合](../src/plugins.ts#L42) 不包含 mcpServers / lspServers；实际传入 `../../outside.json` 和绝对路径仍通过校验，消费者直接 path.resolve 读取。插件已安装即信任是既有政策，但这不能代替组件路径一致的边界校验。 |

## 验证与优先级

本轮运行 **25 个独立针对性检查，全部通过**。检查断言的是当前行为，包括证明误报与证明错误行为；不是“错误已经修复”。探针在忽略目录 `.review-tmp/`，使用独立临时工作区、无害 Node/LSP fixture 和本地 stdio MCP。Windows 命令解析探针只运行无害 echo；没有打开 MCP URL、访问真实凭据或调用付费模型。初次压缩探针生成数据不当，已纠正后重新运行；最终结果为 25/25。

上一轮基线的 175 文件／2,185 项全量通过是已有结果；这轮未重跑全套，因为运行时代码没有改变。`npm run typecheck` 本次通过。静态证据和运行复现已在上表分别标明。

处理顺序建议：

1. WebFetch URL 规范化、项目 LSP 信任门、URL 打开与确认顺序及 Windows shell 输入面。
2. 用户记忆作用域审批、plan 退出的真实批准渠道、MCP 定义变化时批准失效。
3. goal 完成状态持久化、holder 刷新、评估取消／错误降级、headless Terminal 分类和 MCP 配置结构校验。
4. LSP 崩溃恢复与失败清理，再修参数、路径和低优先交互问题。

不建议按原报告直接“修复第 1 项的持久授权”，或移除正常的会话任务隔离：先按已核实的触发路径修复，避免引入额外回归。
