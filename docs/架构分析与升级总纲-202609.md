## 三、核心数据流：一次 query 的生命周期

（完整版见分册 01 §2；此处为总纲级摘要，够用来定位"某个行为发生在哪一步"。）

```
用户输入
  │  TUI: vim/keybindings → InputBox → 提交
  │  （忙时进 InputQueue type-ahead；"!"bash模式；"#memory模式；"/"命令分发）
  │  expandFileRefs(@引用) → beginUserTurn(checkpoint 边界快照)
  ▼
agentLoop（每轮 while）
  STEP 1  上下文准备
          estimateContextTokens(usage基线+增量估算)
          → prepareCheapLayers: 层1边界丢弃→层1.5去重→层2字节裁剪→层3计数microcompact
            （仅在 >150k 阈值时动历史；阈值以下字节稳定以护 prompt cache）
          → 仍超阈值: autoCompact(层5, LLM摘要, 不拆tool对, 失败保原史)
  STEP 2  流式模型调用
          注入 prefetch 附件 + 上批工具 fast-model 摘要（role:"system" 一次性消息）
          text_delta→UI；thinking→UI；tool_use→记录+【只读安全者流内早启动】
          done→usage 基线更新；error→handleModelError(重试/压缩重试/fallback链)
  STEP 3  无工具调用 → 终止判定链
          持久化→Stop hook→输出预算 nudge→length 截断续写→背景通知→队列输入→done
  STEP 4  assistant(tool_calls) 入史（thinking 块随行，否则 API 400）
  STEP 5  executeToolCalls：isConcurrencySafe 贪心分批（保序），安全批并行(≤10)
          每工具: parse→validateInput→PreToolUse hook→工具级权限→系统级权限
                 →审计→投机缓存命中?→watchdog→tool.call→PostToolUse hook→format
          finally 兜底: backfillMissingToolResults 保证 tool_use/tool_result 配对
  STEP 6  grep/glob 结果→投机预取 Read；启动 fast-model 摘要；图片附件；
          合并队列输入与通知 → turnCount+1 → 下一轮
  ▼
每轮结束自动持久化（saveChain 串行 + tmp/rename 原子写）
```

**压缩触发时机总表**：

| 机制 | 时机 |
|---|---|
| 层1 边界丢弃 | 每轮 STEP1（有 COMPACT_BOUNDARY 时物理丢弃前史） |
| 层1.5/2/3 裁剪驱逐 | 每轮 STEP1，仅当估算 > 150k |
| 层5 autoCompact | 便宜层后仍超阈值；或 provider 报 context_length → compact_and_retry |
| 时间型 micro-compact | 仅会话加载时（闲置 ≥60min） |

**缓存策略**：cache_control 三断点（system 稳定前缀 / 最后一个工具 schema / 消息尾块）在 anthropic-adapter；`DYNAMIC_BOUNDARY` 是跨模块契约；prompt-cache.ts 只做断裂**检测归因**（调用前哈希 diff + 调用后 cache_read 降幅 >5% 且 >2000 tokens）。

## 七、中长期架构演进方向（详述）

以下五个方向是超越"逐点修复"的结构性演进，每个都按 现状与动机 → 目标形态 → 涉及文件 → 建议路径 → 风险与注意点 展开。它们彼此独立，可按任意顺序、任意取舍推进。

### 方向一：引入规范化中间表示（IR），终结"以 OpenAI 格式为中立格式"

**现状与动机**
当前 `types.ts` 的消息模型（`Message`/`ToolCall`/`ContentBlock`）本质是 OpenAI Chat Completions 的形状：`tool_calls[].function.arguments` 是 JSON 字符串、`finish_reason` 是 OpenAI 词汇、tool 结果是 `role:"tool"` 消息。Anthropic 路径每轮做"字符串 parse 回对象 → 拼 content blocks"的翻译，OpenAI 路径又做反向 `JSON.stringify`——同一份工具参数每轮双向序列化两次。更实质的代价是**语义双口径**：`usage.input_tokens` 在两条路径含义不同（OpenAI 含缓存、Anthropic 不含），已直接造成 Top10 #3 的复合故障；`SystemMessage` 在两条路径映射为不同角色（system vs user 文本块），模型信任度不同；PDF 只能靠 Anthropic 侧特判、OpenAI 侧必挂；`stop_reason` 的 `refusal`/`pause_turn` 无处安放。每接一个新能力（thinking、effort、document、新 stop_reason）都要在两个 adapter 里各打一个补丁，补丁之间无一致性约束。

**目标形态**
定义一个 provider 无关的消息 IR：
- `ContentBlock` 为封闭判别联合：`text | image | document | thinking | redacted_thinking | tool_use | tool_result`，工具参数在 IR 层就是**对象**（序列化只发生在 adapter 出口一次）。
- `usage` 显式分口径：`billedInput / cacheRead / cacheCreation / contextTokens / output`，每个 adapter 负责把自己的账单映射到这五个字段，映射规则写在类型注释与测试里。
- `stopReason` 为枚举：`endTurn | maxTokens | toolUse | refusal | pauseTurn | contentFilter | unknown`，adapter 做归一化，loop 只消费枚举。
- 角色模型显式声明"内部 system-reminder 消息"如何降级到各 provider（现在是隐式行为差异）。

**涉及文件**
`types.ts`（核心）、`anthropic-adapter.ts`、`llm-adapter.ts`（双向映射层）、`agent-loop.ts`（消费点）、`tool-executor.ts`（arguments 序列化点）、`token-estimator.ts`、`session-memory.ts`（持久化格式兼容）。

**建议路径**
1. 先在 `types.ts` 里**新增** IR 类型与 `usage` 分口径字段，两个 adapter 填充新字段但保留旧字段（双写期）。
2. agent-loop / TUI 的消费点逐个切到新字段（Top10 #3 的修复就是第一个消费者，可借势完成）。
3. 持久化格式 bump 到 v4，迁移函数把旧 v3 会话的 usage 按 provider 标记换算。
4. 最后删除旧字段与双向序列化的中间形态。

**风险与注意点**
- 持久化兼容：v3 会话的 `arguments` 字符串与 usage 语义都要能迁移，`SESSION_FORMAT_VERSION` 迁移链（session-memory.ts:79-137）是现成模式。
- IR 不要过度设计：只需覆盖当前两个 provider 家族的语义并集 + 明确的 unknown 兜底，不必为想象中的 provider 预留。
- 双写期要有测试锁住"新旧字段一致性"，否则切换中途两种口径并存会比现在更乱。

### 方向二：配置中心化——把散落 6+ 模块的魔数与环境变量收敛为单一 config 层

**现状与动机**
压缩阈值 150k/200k（agent-loop）、team 私有阈值、workflow 50k、`MAX_NOTIFICATION_CONTINUATIONS=10`、TAIL_SIZE=20、头600/尾400 裁剪、2000 tokens/5% 断裂判定、5min watchdog、30min 上限、3s glob TTL、60min 闲置 micro-compact、8000 字符 skill 发现预算……全部硬编码在各自模块；环境变量开关三套前缀并存（`CCR_*`、`CLAUDE_CODE_*`、`DEBUG_*`），分散在 6+ 个模块各自 `process.env` 读取。后果：① 阈值与模型上下文窗口无关（provider-profiles 没有任何 contextWindow 元数据），换 32k 小模型或 1M 大模型行为都不对；② 同一关切（如并发上限）在不同工具各自为政；③ 无人能一眼回答"这个系统有哪些可调参数、默认值是什么"。

**目标形态**
一个 `src/config/` 模块：
- **模型元数据表**：每 provider/模型族的 `contextWindow`、`maxOutput`、`supportsEffort`、`supportsThinking`、`supportsDocuments`、定价——成为压缩阈值、effort 门控（分册 02 §6-5）、session-stats 定价表的**单一数据源**（现在三处各维护一份子串匹配表）。
- **派生默认值**：`autoCompactThreshold = contextWindow × 0.85` 之类的公式，魔数变成有出处的派生量。
- **统一 env 层**：一个带 schema（zod）的 env 解析入口，产出强类型 `RuntimeConfig`，各模块注入消费而非自读 `process.env`；三套前缀做别名归一并在 `/doctor` 里报告生效值。
- `/config` 命令可视化当前全部生效配置与来源（env/settings/默认）。

**涉及文件**
新建 `src/config/`；改造 `agent-loop.ts`、`context-pipeline.ts`、`provider-profiles.ts`、`session-stats.ts`、`micro-compact-config.ts`、`tool-executor.ts`、`speculation.ts` 等消费点；`commands/config.ts`、`commands/doctor.ts` 接入。

**建议路径**
1. 先盘点（可让一个子代理全仓 grep `process.env` 与数字字面量，产出参数清单表存入 docs）。
2. 建模型元数据表并让三个现有消费者（压缩阈值/effort 门控/定价）切换——这一步与分册 01 §6-8、02 §6-5 天然重合。
3. 再收环境变量（机械劳动，量大但风险低，适合分批）。

**风险与注意点**
- 不要一步到位搞"大配置对象贯穿全栈"——那会制造新的上帝对象。按关切分片（模型能力片、压缩片、并发片、UI 片），各片独立注入。
- 现有 `CCR_*` 变量是用户可见契约，改名须保留别名期。

### 方向三：消灭"双胞胎漂移"——重复实现的系统性合并

**现状与动机**
本次审查发现的重复实现已形成模式（每个都独立审查确认过）：
| 双胞胎 | 漂移后果 |
|---|---|
| Task ↔ Agent（~70% 重复） | fork 深度 1 vs 2、maxTurns 10 vs 20、sessionId 共享 vs 后缀 → 同名 "fork" 在两个工具下 read-before-edit 语义不同 |
| bash ↔ powershell（~130 行逐行重复） | 后台溢出度量已漂移（`stdout.length` vs `Buffer.byteLength`）；PowerShell 缺 run_in_background |
| `isContextLengthError` × 2（error-recovery / llm-adapter） | 必然漂移，且 H2 修复要改两处 |
| schedule_cron+sleep ↔ CronCreate 三件套 ↔ ScheduleWakeup | 6 个调度工具并存，模型选择困惑 |
| todo ↔ TaskCreate 四件套 ↔ team task_list ↔ job_list | 4 个"列表"面 |
| 三个磁盘 loader（commands/skills/agents） | 90% 同构；trustedShell bug 在两个 loader 里各犯一次 |
| Edit/MultiEdit errno 映射块逐字重复 | 低风险但未收敛 |
| Ink PermissionPrompt ↔ raw-mode promptPermissionMenu | 权限 UI 两份实现 |

这不是单点问题而是**工程纪律问题**：项目习惯"复制一个近亲再改"，每个复制体随后独立演化。审查中至少 4 个实际 bug（sessionId 撞桶、度量不一致、trustedShell 双犯、H2 双实现）直接源于此。

**目标形态**
- 每对双胞胎抽共享核心（`spawnSubagent(opts)`、`runShellProcess(dialect)`、`loadDiskExtension(kind, roots, {trusted})`），差异变成参数。
- 面向模型的工具面收敛：调度一套、任务清单一套（或明确分层命名，如 team 系全部 `team_*` 前缀）。
- 立一条可执行纪律（写入 CLAUDE.md + code review 检查项）："新工具/新 loader 必须先找可共享骨架；无法共享要写明理由。"

**建议路径**
从**漂移已造成 bug** 的对子开始（Task/Agent、bash/powershell、两个 isContextLengthError），它们合并的动机最充分、验收最明确（现有测试 + 行为统一断言）；工具面收敛（调度/清单）涉及模型可见契约变更，需要单独设计迁移期（旧名保留为 alias 一个版本周期——这反过来要求先解决 aliases 死元数据问题，见分册 03 §6-4，两件事应联动规划）。

**风险与注意点**
- 合并 Task/Agent 时两侧测试都要保留并通过，行为差异（fork 深度等）要显式决策"统一到哪个值"而不是随手取一边。
- 工具改名/删除影响旧会话回放与用户肌肉记忆，`design-sync` 的"诚实禁用桩"模式（保留 schema、isEnabled false、调用返回明确失败）是现成的退役范式。

### 方向四：诚实性清扫——消除"宣称与实现不符"的系统性风险

**现状与动机**
审查发现至少 10 处"注释/文档/参数描述宣称 X，代码实际做 Y"：
1. `run.tsx:1533` "Enable mouse input for scrolling support"——从未开启鼠标上报。
2. `/branch` 头注释 "resumed immediately"——实际不切换。
3. trustedShell 头注释"只有用户级可信"——`index===0` 使项目级获信（安全事故级）。
4. MCP 信任门注释声称防供应链攻击——路径不匹配使其为死代码（安全事故级）。
5. `system-prompt.ts:101-106` 注释"只放 name+intent 避免双倍 token"——实际 dump 全文。
6. `save()` 注释 "captures snapshot"——实际捕获可变引用。
7. evictionStub 承诺 "recoverable via RestoreContext"——store 已死。
8. workflow promptDescription "Workers run read-only"——授予了 bash。
9. `sandbox/` 目录名暗示沙箱实现——实为一次性测试项目。
10. TUI_IMPROVEMENTS.md 整篇过期仍存于仓库根。

这类背离比 bug 更危险：**它们污染后续维护者（包括未来 plan 会话中的 LLM）的安全假设**。#3/#4 已经证明这一点——注释宣称的防线不存在，而读注释的人会以为存在。

**目标形态**
- 一次性专项：对上述 10 处逐一"改代码兑现宣称"或"改宣称如实描述"，二选一，不许留背离。
- 建立轻量机制：CI 里加一个"宣称审计"清单文档（docs/），每次触碰相应模块时核对；或约定注释规范——安全相关注释必须附"验证方式"（测试名或 grep 锚点）。
- 长期：把"安全宣称"尽量从注释升格为**测试**（如"项目级 MCP 配置必经信任门"应是一条集成测试，而不是 mcp/index.ts:178-184 的一段注释）。

**建议路径**
10 处清单已在各分册标注，逐条处理即可，每条都是小改动。适合与方向三/各分部修复顺路完成（修 trustedShell 时顺手改注释、修 MCP 门时顺手补测试）。

**风险与注意点**
- 唯一需要决策的是方向（兑现 vs 改口）：如鼠标支持，"兑现"是一个中型特性，"改口"是删一行注释——按需求优先级选，但**不能不选**。

### 方向五：测试盲区补齐——从"正向路径单元覆盖"到"跨模块契约测试"

**现状与动机**
项目有 148+ 测试文件、1812 个用例，单元覆盖不可谓不勤。但本次审查发现的全部高危缺陷（Top10 #1 MCP 信任门、#2 trustedShell、#3 usage 基线、#4 失败输出丢失）有一个共同特征：**都发生在模块交界处，且每个模块自己的测试都是绿的**。
- MCP 信任门的单测（integration-mcp.test.ts:337-369）显式传 `requireTrust:true` 测门本身——门是好的，但生产接线永远不会打开它；没有一条测试从"发现项目配置"走到"信任判定"。
- 失败输出丢失：bash 测试断言 `result.content/error` 字段都在——但没断言**模型最终看到的 formatted 字符串**含输出。
- usage 基线：adapter 测试断言 usage 字段解析正确，loop 测试注入的 usage 是理想值——没有一条测试锁"Anthropic 高缓存命中场景下 estimateContextTokens ≈ 真实 prompt 大小"。

**目标形态**
新增一类**契约测试**（tests/contract/ 或 __tests__/contract-*.test.ts），每条对应一个跨模块不变量：
1. **安全门端到端**：从磁盘 fixture（含 `.claude/mcp.json`、`.claude/commands/*.md` 的项目目录）启动装配流程，断言"未经信任确认不 spawn / 不执行 shell"。
2. **provider 语义一致性**：同一逻辑场景（高缓存命中、context 超限、429 带 Retry-After、529、PDF 输入）分别走两个 adapter + loop，断言压缩触发时机、重试行为、错误呈现一致。
3. **信息保真**：任意工具的失败路径，断言模型可见的 formatted 输出包含诊断信息（stdout/stderr、错误分类）；遍历注册表对每个工具跑"失败快照"。
4. **宣称即测试**：方向四清扫出的每条安全宣称，落一条对应断言。
5. **顺序语义**：`Write(f)+Read(f)` 同消息场景断言 Read 看到新内容（锁 H3 修复）；Edit 后 Read 断言非陈旧（锁 H4 修复）。

**建议路径**
契约测试与修复联动：每修一个 Top10 项，先写复现测试（红）再修（绿）——这同时解决"修了但没锁住"的回归风险。第 3 类（信息保真遍历）可以一次性写完，它独立于其他修复。

**风险与注意点**
- 契约测试要跑真实装配路径（真 loader、真 registry、mock 网络/LLM），不能重蹈"单测里手工传对参数"的覆辙——#1 的教训正是"测试环境里参数是对的，生产接线是错的"。
- 控制运行成本：契约测试可以单独 vitest project/标签，CI 必跑、本地 watch 可排除。

### 五个方向之间的关系

- 方向一（IR）是方向五第 2 类契约测试的**结构前提**——语义显式化之后才谈得上一致性断言。
- 方向二（配置中心化）与方向一共享"模型元数据表"这一基石（contextWindow 既是压缩阈值来源也是 IR usage 语义的注解）。
- 方向三（双胞胎合并）的 aliases/工具面收敛依赖方向四（诚实性）先明确"每个宣称的处置方向"。
- 方向五贯穿所有：每个分部的修复都应以契约测试收口。
