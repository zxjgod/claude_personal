# `--tmux`：官方判定级联的完整复刻（2026-10-03）

对标本机官方 CLI **2.1.202**（`C:\Users\20616\AppData\Roaming\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe`，win32 native binary）。

## 结论先行

`--tmux` 在 Windows 上**没有任何成功路径**。官方 win32 构建把这个 flag 的实现整个编译成了一句硬错误。本项目复刻了这条判定级联的每一句文案，并且**实测逐字对齐**。

更值得注意的是：官方 `--help` 对这个 flag 的描述**有两处与运行时不符**，两处都已实机证实。这是 `--betas`（看着是透传，实为白名单）、`--from-pr`（声明承诺交互式选择器，实机在非 TTY 下什么都不做）之后的第三次。

## 官方运行时考古

### 1. 有一条跑在 commander 之前的"快速路径"

`--tmux` 并不走普通的 commander 解析。入口处有一段提前判断（binary offset `250004989`）：

```js
if ((t.includes("--tmux") || t.includes("--tmux=classic"))
    && (t.includes("-w") || t.includes("--worktree") || t.some(f => f.startsWith("--worktree=")))) {
  telemetry("cli_tmux_worktree_fast_path");
  let { isWorktreeModeEnabled: m } = await import(/* ABl */);
  if (m()) {
    let { execIntoTmuxWorktree: h } = await import(/* TR */);
    let g = await h(t);
    if (g.handled) return;
    if (g.error) exitWithError(g.error);
  }
}
```

**触发条件是"命令行上同时有 `--tmux` 和一个 worktree flag"**，与顺序无关。没有 worktree flag 时这条路径根本不触发，`--tmux` 落回普通解析，被另一段代码（offset `249873633`）以 `Error: --tmux requires --worktree` 拒掉。

顺带一个细节：`xTt()`（`isWorktreeModeEnabled`）的函数体是 `return !0` —— 永远为 true 的特性开关桩。

### 2. win32 构建里，这条路径是两句硬错误

`execIntoTmuxWorktree` 就是 `cLp`（offset `233380267`），在 win32 构建里**全文只有两行**：

```js
async function cLp(e) {
  if (!sd()) return { handled: !1, error: "Workspace trust not yet accepted. Run `claude` once in this directory and accept the trust dialog, then retry with --worktree." };
  return { handled: !1, error: "Error: --tmux is not supported on Windows" };
}
```

真正会创建 tmux 会话的 `createTmuxSessionForWorktree`（`L_o`）、`generateTmuxSessionName`（`gjr`）、`killTmuxSession`（`tht`）都在同一个导出表里，但在 win32 chunk 里**永远走不到**。平台分支是编译期烘进去的，不是运行时探测的。

### 3. `--tmux=classic` 根本不存在

`--help` 写着：

```
--tmux   Create a tmux session for the worktree (requires --worktree). Uses iTerm2
         native panes when available; use --tmux=classic for traditional tmux.
```

但注册是（offset `266695759`）：

```js
e.option("--tmux", "Create a tmux session for the worktree (requires --worktree). …")
```

**无值占位符**。commander 因此拒绝一切 `--tmux=<v>` 拼写，报 `error: unknown option '--tmux=classic'`。文档推荐的逃生口在 CLI 上是不存在的。

顺带一个更细的怪癖：快速路径只字面比较 `"--tmux=classic"`。所以 `--tmux=classic -w x` 走快速路径（得到 Windows 错误），而 `--tmux=other -w x` 绕开快速路径、落到 commander（得到 unknown option）。同一个"带值"形状，两个不同结果。本项目保留了这个可观测差异。

### 4. tmux 安装指引（`getTmuxInstallInstructions`，offset `252991714`）

```js
function unf() {
  switch (Vt()) {
    case "macos":  return `To use agent swarms, install tmux:\n  brew install tmux\n…`;
    case "linux":
    case "wsl":    return `To use agent swarms, install tmux:\n  sudo apt install tmux    # Ubuntu/Debian\n  sudo dnf install tmux    # Fedora/RHEL\n…`;
    case "windows": return `To use agent swarms, you need tmux which requires WSL (Windows Subsystem for Linux)…`;
    default:        return `To use agent swarms, install tmux using your system's package manager.\n…`;
  }
}
```

四点值得记：平台 token 是 `"macos"` 而**不是** `"darwin"`；`wsl` 与 `linux` 共用 apt+dnf 那段；Windows 那段走 WSL 措辞，但在 win32 构建里因为平台门先拦而**不可达**；文案里的 "agent swarms" 是官方在 `--tmux` 与 swarms 之间共用一个 helper 的结果，本项目逐字保留以保持一致。

### 5. 官方自己的四级顺序

| # | 条件 | 消息 |
| --- | --- | --- |
| 1 | 无 worktree flag，裸 `--tmux` | `Error: --tmux requires --worktree` |
| 2 | 有 worktree flag，workspace 未信任 | ``Workspace trust not yet accepted. Run `claude` once in this directory and accept the trust dialog, then retry with --worktree.`` |
| 3 | 有 worktree flag，已信任，平台是 Windows | `Error: --tmux is not supported on Windows` |
| 4 | 非 Windows，tmux 未安装 | `Error: tmux is not installed.` + 分平台指引 |

第 2 条挡在第 3 条之前，是本轮唯一一处**静态读到、且实测撞上过**的顺序证据。

### 6. BackendRegistry 的 8 分支（本项目不实现，仅存档）

`detectAndGetBackend`（offset `236214000`）的选择级联：`teammateMode==="iterm2"` 显式要求（两种各自具名的错误）→ 已在 tmux 内 → iTerm2 内 → it2 CLI → iTerm2 内回退 tmux（`needs_it2_setup` 提示 `pip install it2`）→ iTerm2 内且无 it2 无 tmux → 外部 tmux 会话 → `No pane backend available`。

### 四条设计决策

1. **校验前置于 worktree 创建** —— 官方快速路径跑在一切之前，所以被拒的 `--tmux` 在 Windows 上根本不碰磁盘。本项目照抄这个顺序；实测 `--tmux --worktree probe` 得到的是 Windows 错误而不是 `Cannot create a worktree`，顺序已被验证。
2. **不复刻官方那道 workspace trust 门** —— 官方的判据是 `projects[cwd].hasTrustDialogAccepted === true`（整目录信任对话框），本项目的判据是项目 `ALLOW` 规则的指纹（`confirmProjectAllowRules`）。两者不同源。照抄文案等于宣告一个本项目不存在的对话框，而本项目自己的门仍在原位运行。**代价**：未信任 workspace 上本项目直接给第 3 条、官方给第 2 条；终局（exit 1）相同。
3. **平台门先于 `tmux -V` 探测** —— 官方就是这个顺序。这一条是**被自己的测试逼出来的**：初版在 Windows 上也会 spawn 一次 `tmux -V`，只为被告知"tmux 在这里无关"。已加短路。
4. **tmux 已装但 pane 未实现 → 显式失败，并点名缺的是哪一段** —— 静默忽略会让 `--tmux` 看起来生效了。文案明确区分"系统缺 tmux"（给安装指引）和"本 build 缺 pane 会话创建"（给替代写法），两者不混。

### 明确记录的偏差

1. 不复刻 workspace trust 门（第 2 条），理由见上
2. Windows 上不 spawn `tmux -V`（与官方一致，是优化不是偏差，但本项目把它固定成了测试断言）
3. tmux 存在时本项目报"未实现"而非降级为普通 worktree 会话

### 明确未实现（不应暗示已具备）

- tmux pane 会话创建（`createTmuxSessionForWorktree` / `generateTmuxSessionName` / `killTmuxSession`）
- iTerm2 原生 pane 后端（官方在检测到 iTerm2 + `it2` CLI 时走这条，是 `--tmux` 的**默认**路径）
- agent swarms 的 pane 编排、`teammateMode` 后端选择、BackendRegistry 的 8 分支级联
