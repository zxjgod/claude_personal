# PDF 故障修复与多模态检查

## 故障原因

当前 `.env` 使用 `anthropic` 协议、`k3` 模型和 Kimi Coding 接口。Read 原先将 PDF 字节存入 `images`，agent-loop 再将附件作为 user 消息加入会话历史；Anthropic 适配器将其转为原生 `document`。该接口不接受这一 PDF 输入，合法的小型 PDF 也返回 `400 invalid_request_error: Invalid request Error`。历史附件持续留在请求中，因此之后发送“继续”仍重复失败。

OpenAI 兼容路径原先会在本地拒绝 PDF，但已有附件同样留在历史中，后续请求也无法恢复。这属于附件格式和会话恢复问题，不是 PDF 文件过大或模型思考卡死。

## 已实施

- PDF 使用 PDF.js 在本地提取文字并渲染 PNG 页图，两个 API 适配器均发送普通图片，不依赖供应商原生 PDF 功能。
- Read 新增 `pages`，接受单页或连续范围，每次最多 5 页，默认前 5 页。结果保留页码、总页数和继续读取范围；PDF 不接受文本行参数 `offset/limit`。
- PDF 上限 20 MiB，页图每批合计上限 5 MiB。页图最长边 1568 像素、最多约 200 万像素；每页提取文字最多 20000 字符。
- 解析与渲染在独立 Worker 线程中执行，设置 30 秒超时、取消信号与 256 MiB V8 堆限制。堆限制不等同于整个进程或原生图像库的内存硬限制。
- 损坏 PDF、越界页码、超时等返回工具错误，不将原始 PDF 注入新会话。旧会话中的 PDF 在 API 请求边界自动转换；无法转换的附件以明确的未读取提示替代，原始历史保持可恢复。
- 已知纯文本模型只接收 PDF 提取文字；普通图片在 Read 阶段明确拒绝。历史图片和剪贴板图片在发送时替换为未读取提示。自定义接口可通过 `LLM_SUPPORTS_IMAGES` 或 SDK `options.supportsImages` 覆盖自动判断，未知模型默认尝试图片输入。
- 构建与 npm 发布包包含 PDF Worker；PDF.js 字体、CMap、WASM 和 Canvas 通过运行依赖加载，不在主 CLI 启动时导入。

## 能力边界

| 输入 | 当前处理 | 边界 |
| --- | --- | --- |
| PNG/JPEG/GIF/WebP | Read 发送图片；剪贴板发送 PNG | 单张最大 5 MiB，普通图片暂未自动缩放或校验完整解码 |
| 文本 PDF、表格、流程图 | 分页提取文字并渲染 PNG | 默认读取前 5 页；小字图纸可能需要局部截图 |
| 扫描 PDF | 渲染页图给视觉模型 | 无独立 OCR；纯文本模型不能读出扫描内容 |
| 旧会话中的 PDF | 请求前转换为文字与 PNG | 文件损坏或超限时提示重新读取 |
| Notebook | 展示代码和 Markdown 单元 | 不展示富媒体输出图片 |
| 音频、视频、DOCX 等其他二进制 | 未实现媒体解析 | 不应宣称可直接理解 |

后续适合补充普通图片的解码校验与尺寸归一化，尤其是超大截图和损坏图片；如需要长视频、音频或 DOCX，应单独设计读取工具，不复用 image 通道。

## 验证

- 对截图对应的 `S32G3_RD1_RD2_开启与复位流程.pdf` 实测：共 14 页，中文文字提取正常，首页渲染为 1109 × 1568 PNG，约 251 KB。
- 真实 Kimi 接口：原生 PDF 复现同样的 400；发送实际首页图片且不提供提取文字，模型正确回复标题与页码 `1 / 14`。
- 真实 Kimi 接口：带旧格式 PDF 附件的继续请求成功返回，无原生 PDF 进入请求。
- 测试覆盖分页、无文本图形页、非空像素、损坏文件、大小上限、非法范围、超时、取消、文本模型降级及两个供应商适配器。
- 发布包检查通过本地 HTTP 测试服务实际调用解包后的适配器，验证 PDF 文字和 PNG 渲染及 Worker/字体资源定位，不调用外部模型。
