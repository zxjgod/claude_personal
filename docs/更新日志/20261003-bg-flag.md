# `--bg` / `claude agents`：判定层完整复刻，运行时显式拒绝（2026-10-03）

对标本机官方 CLI **2.1.202**（win32 native binary）。

## 结论先行

`--bg` / `--background` 是**真 flag**："Start the session as a background agent and return immediately (manage with `claude agents`)"。但它**不是**一个孤立开关 —— 它是一整个跨进程子系统（守护进程 + PTY 名册 + 任务存储 + attach 复用器 + 交互视图）的入口。help 对它撒了**三次**谎，本项目按"判定层完整复刻 + 运行时半显式拒绝"处置。

## 官方 `--help` 的三次撒谎（全部实机验证）

### 谎一：`Commands:` 段只列 1 个，实际 7 个

`claude --help` 的 Commands 段只有 `agents` 一条。但有一条**跑在 commander 之前**的 fast path（offset `249998849`）实际分发**六个**隐藏子命令：

```js
if (t[0]==="logs" || t[0]==="attach" || t[0]==="stop" || t[0]==="kill"
    || t[0]==="respawn" || t[0]==="rm" || t.includes("--bg") || t.includes("--background")) { … }
```

`logs` `attach` `stop` `kill` `respawn` `rm` 全部不在 help 里。而 `--bg` 成功后的 banner 却让用户去用其中三个：

```
backgrounded · a764094c (idle — send a prompt to start)
  claude agents             list sessions
  claude attach a764094c    open in this terminal
  claude logs a764094c      show recent output
  claude stop a764094c      stop this session
```

### 谎二：`--bg` 与 `--print` 硬冲突，注册表只字未提

```bash
$ claude --bg -p hi
--bg and --print conflict: --print never starts the interactive session that
`claude agents` attaches to, so the job would be unattachable. The prompt is
the positional — drop --print: `claude --bg '<task>'`.     exit=1
```

prompt 必须是位置参数，`--print` / `-p` 一律拒绝。选项注册表里没有任何提示。

### 谎三：`claude rm --help` 自称 "works on already-exited sessions"，实测对 done 任务永远失败

`rm` 的帮助明写 "Unlike `stop`, works on already-exited sessions." —— 这正是它声称能处理的情形。但实测：

```bash
$ claude rm a764094c        # a764094c 已 done
couldn't confirm a764094c was stopped — the background service may be restarting.  exit=1
$ claude stop a764094c      # 补刀也不行
couldn't confirm a764094c was stopped — the background service may be restarting.  exit=1
```

`rm` 内部先 stop 再删；`done` 任务无法 stop，于是**永远无法通过工具删除**。这是我探针留下的那个 `done` 任务 `a764094c`，官方工具对它束手无策。**官方 2.1.202 的真实 bug**，与其自己的帮助文案直接矛盾。

### 预检冲突（`ZEm`，四项，序固定）


第一项是**另一整个隐藏后端**（`--cloud` / `--remote`），文案："--bg and --cloud are different backends. Use `claude --cloud '<task>'` directly…"。

### `kill` 是 `stop` 的纯别名

dispatch switch 没有 `kill` 分支，落到同一个 `stopHandler`。搜 "claude kill <id>" 在整个二进制里为空 —— 这就是为什么它**没有自己的 usage 行**。

## 实机探针

- `claude --bg --help` **真的 spawn 了一个后台会话**（`a764094c`）——`--bg` 跑在 commander 解析之前
- gate 关闭（`CLAUDE_CODE_DISABLE_AGENT_VIEW=1`）：`'--bg' is disabled by CLAUDE_CODE_DISABLE_AGENT_VIEW.`，exit 1，**不 spawn**
- `stop` / `logs` 未知 id → `No job matching '<id>'. Run 'claude agents' to list running sessions.`
- `rm` 未知 id → `No job matching '<id>'`（**无** agents 后缀 —— 它用自己的 inline resolver）
- `stop` / `attach` 无参数 → `Usage: claude stop <id>` / `Usage: claude attach <id>`，exit 1
- `agents` 子命令**也过门**：`'claude agents --json' is disabled by …`（只读 fast path 片段会漏掉这点）
- `--bg-spare` / `--preload` 是**独立入口**，不过门（`[bg-spare] missing claim sock path`，exit 2）

### 设计决策

1. **判定序严格对齐官方**：子命令/flag 检测 → 特性门 → 预检冲突。门在前意味着 `--bg --print` + 门关闭时报门而非 print 冲突 —— 这个序是**可观测的**，写进测试。
2. **拒绝文案分两类**：官方已有文案的（gate / print / cloud / bypass / auto / usage / no-match / ambiguous）逐字复刻；官方没有文案的（真正 spawn 的那一刻）用点名缺口的本项目文案。**永不静默降级**。
3. **`rm` 的 agents 后缀单独处理**：官方 `rm` 用自己的 inline resolver 且无后缀，做成 `resolveJobIdArg` 的 `agentsHint` 选项，`kill` 走 stop 的 usage 与 summary。
4. **校验前置于 worktree/tmux**：背景任务绝不能在通往拒绝的路上碰 worktree 或 tmux pane。

### 明确记录的偏差

- **运行时半全部未实现**。没有 daemon，所有会触碰进程/文件系统的路径都以点名缺口的拒绝收尾（exit 1）。这与 `--tmux` 的处置一致。
- `selectsPrint` 未重建官方的短旗簇剥皮（`-xp` 命中 print）—— `Rge` 的确切切分规则无法从二进制复原，猜测会在无辜 token 上误报。代价是：一条已拒绝路径上换一个拒绝文案，不会误判。
- `bypassAccepted` / `autoOptedIn` 是注入参数，默认 `undefined`（即官方 `false`）——本项目没有交互式免责声明状态，因此 `--bg --dangerously-skip-permissions` 会以官方原句拒绝（正确且 fail-closed）。
