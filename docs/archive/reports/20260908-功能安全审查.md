## 1. [P1] PowerShell 只读判定允许嵌套写操作和敏感读取

位置：`src/tools/utils/command.ts:187–220`。

过滤器拒绝 `$()` 和脚本块，但未拒绝普通圆括号表达式；随后仅根据命令前缀判断只读。例如 `Write-Output (Set-Content -LiteralPath review-marker.txt -Value changed)` 被标为只读。系统在检查计划模式前直接放行只读工具，因此计划模式也能执行写入。`Get-Content .env` 同样自动放行，PowerShell 分支没有调用 Bash 分支已有的敏感路径检查。

验证：通过真实 `executeSingleTool` 流程运行上述嵌套表达式，将最终执行函数替换为 spy；计划模式下执行函数被调用，拒绝审批回调未被调用。另验证 `Get-Content .env` 权限结果为允许。未实际执行这些命令读取真实文件。

建议：使用 PowerShell AST 验证完整表达式，只允许明确的命令和参数组合；不能证明只读时走审批。补齐路径及环境变量敏感信息控制。

## 2. [P1] Bash 白名单忽略可写选项及执行辅助程序的选项

位置：`src/tools/utils/command.ts:150–160`。

`sort input.txt -o output.txt`、`git diff --output=review.patch`、`git reflog expire --expire=now --all`、`rg --pre=review-helper.exe probe input.txt` 均被判为只读。它们分别具有写文件、修改仓库历史记录或执行辅助程序的能力。默认模式跳过审批，计划模式也直接允许。具体命令能否执行取决于平台及相应程序是否安装。

验证：以上四种输入调用实际 `checkPermission`，计划模式且审批回调固定拒绝时仍全部返回允许。没有执行清理 reflog 等破坏性命令。

建议：逐项校验参数和 Git 子命令；禁止输出文件、预处理器、外部执行等选项。不能仅凭可执行文件名称认定只读。

## 3. [P1] Grep 绕过敏感文件禁止读取策略

位置：`src/tools/core/grep.ts:122–134`。

Grep 对 `path` 只检查工作区边界，没有检查 `isBlockedPath`；系统权限层仅检查名为 `filePath` 的参数。显式指定 `.env` 可使 ripgrep 读取该文件，即便 Read 明确禁止读取。

验证：在临时工作区创建包含 `REVIEW_FAKE_SECRET=not-a-real-secret` 的 `.env`；Read 返回 blocked，Grep 的权限检查返回允许，实际 Grep 调用成功返回该行。

建议：显式搜索目标与枚举出的每个文件都使用统一的真实路径和敏感路径校验，覆盖 ripgrep 与 Node 回退分支；不能将忽略隐藏文件当成权限控制。

## 4. [P1] 子代理审批遗漏 PowerShell，父级拒绝不生效

位置：`src/utils/subagent-security.ts:20–48`；调用链见 `src/tools/extended/agent.ts:230`、`src/tools/extended/task.ts:229`、`src/team.ts:237`。

审批函数只把固定列表中的工具转发给父级，未列出的工具全部返回 true。PowerShell、REPL 及未来新增的可写工具不能依靠这份名单获得可靠的审批。对于拥有 PowerShell 工具的子代理，即使输入被正确识别为可写，也不会询问父级。

验证：父审批回调固定返回 false；对被识别为非只读的 `Set-Content review-marker.txt changed` 调用实际权限检查，结果允许，父级回调调用次数为 0。

建议：基于工具能力判断，需审批的操作统一转发父级；没有父级审批能力时默认拒绝。不要将未知工具等同于只读。

## 5. [P1] WebFetch 的 SSRF 防护未校验 DNS 解析结果

位置：`src/utils/input-validator.ts:197–209`；网络调用见 `src/tools/extended/web-fetch.ts:223–228`。

只拦截字面 IP 和精确等于 `localhost` 的名称，普通域名直接允许。解析到内网的域名仍能进入 fetch；逐跳重定向检查使用同一个校验器，无法解决此问题。`localhost.` 是一个直接的绕过例子。若本机或内网存在可由 GET 访问的服务，模型可通过自动批准的 WebFetch 访问它。

验证：`http://localhost.:34567/probe` 的校验结果为允许，本机 DNS lookup 将 `localhost.` 解析到环回地址。未向该端口发送 HTTP 请求。

建议：严格限制 HTTP/HTTPS，解析并校验所有 A/AAAA 地址，在连接时固定已验证地址，保留正确的 Host/SNI；每次重定向重复此流程，防止再次解析导致 DNS rebinding。

## 6. [P1] MCP OAuth 令牌仅按名称缓存，可跨服务器泄露

位置：`src/mcp/auth.ts:68–79`。

构造函数接收服务器 URL 但完全忽略，令牌文件只由经过字符替换的服务器名称决定。不同项目使用相同服务器名称、修改某个名称对应的服务器地址，或者名称清洗发生碰撞，都可能读取之前服务器的访问令牌。SDK 会把 `tokens()` 的结果直接添加到请求的 Authorization Bearer 头，新的服务器有机会获得旧令牌；不需要旧令牌在新服务器上有效。

验证：两个相同名称、不同 HTTPS 域名的 provider 使用同一个临时认证目录，第二个读到了第一个保存的假令牌。另核对本地 MCP SDK 的 `streamableHttp.js:61–63`，确认令牌用于请求头。没有发送令牌或真实网络请求。

建议：缓存键包含规范化服务器 URL/资源标识及客户端身份，使用无碰撞哈希；读取时核对绑定元数据，地址变化时重新授权。

## 7. [P2] DesignSync 返回写入成功，但没有实现保存

位置：`src/tools/extended/design-sync.ts:127–156`、`403–412`。

实际实例化的 DesignSystemAPI 仍为 Mock：写入、删除及资产注册均无实际动作，读取固定返回空值。工具却回复 `Wrote ...` 等成功消息，`localPath` 也被忽略。这会让用户及后续模型流程误认为数据已上传或保存。

验证：finalize_plan 后调用 write_files 得到成功消息，紧接着 get_file 返回 not found。全部在内存中运行。

建议：接入真实实现和读回验证；接入之前禁用该能力或明确返回“未实现”，禁止报告虚假的操作成功。
