# 局限性说明（当前边界与历史记录）

> 当前版本：v1.6.1，2026-10-02。实际能力与验证见 [全面升级日志](../../更新日志/20261002-comprehensive-upgrade.md) 和 [审查修复](../../更新日志/20261002-review-remediation.md)。下面分隔线后的旧版说明保留为历史记录；其中 LSP、投机读取、测试数量与 user memory 等条目不再代表当前代码。

## 当前仍存在的边界

- 官方订阅认证、托管云端、Remote Control、Chrome 官方扩展、IDE 客户端界面、语音服务和 Mods 运行时未移植；新增 MCP 与 SDK 是公开接入方式，不是这些官方产品的替代实现。
- 通用 LSP 已实现，但需要安装对应语言服务器。TypeScript / JavaScript 可使用项目内置 tsserver。
- 非交互模式有实时输入、结构化校验、会话保存与本地 TypeScript / Python 接口；官方 Agent SDK 的所有控制消息和审批回调仍未完整复现。
- 模型效果随 provider、模型与任务变化；单元与模拟集成测试不能证明真实编码效果等同官方。新增评估脚本可做同任务对照，此轮没有执行付费模型评估。
- 预算使用已知模型价格、token 估算和并发预留，不能替代供应商账单的硬限制；发生错误且没有 usage 时采用保守预留估算。
- 配置与扩展支持常用标准字段，不代表官方所有字段与动态行为完全兼容；未消费的顶层设置继续报告诊断。
- 会话快照与运行状态文件分别保存，不构成跨文件事务。运行中的后台进程不会在恢复会话时自动复活；历史结果与中断状态可以恢复。
- 保留既有安装即信任、best-effort 降权和 Shell 修改不进入 checkpoint 的设计取舍。

## 历史说明

> 本文档是项目的**诚实声明**。相比 [`项目总览.md`](../../项目总览.md) 里"生产就绪 / 90% 对齐官方"这类表述，这里只写**无法证实、尚未做到、或实现偏浅**的部分。
>
> 写这些不是为了贬低项目，而是让使用者对「它能做什么、不能做什么、风险在哪」有准确预期。**这是项目里最该先读的一页。**

---

## 一、先说定位：这是个什么项目

`claude_personal` 本质是**逆向 Claude Code 架构、对齐第三方 LLM API 的复刻 / 学习项目**。

- 它做到了「架构研究与个人 / 小团队本地工具」这一档，而且做得扎实（类型安全、测试充分、核心抽象正确）。
- 它**不是**可商业化的产品，也没打算是。把它当成"能对标官方 Claude Code 的成熟产品"来用，会失望。

---

## 二、"90% 对齐官方"无法证实

文档里"90% 对齐官方 Claude Code"是**自评数字，没有任何客观比对手段**：

- 官方 Claude Code 是闭源的、多年迭代的商业产品，无法拿到它的内部实现做逐项对齐。
- 项目自己内部就**自相矛盾**：[`20260623-项目评审报告.md`](20260623-项目评审报告.md)（2026-06-23，通读全部源码后的评审）给出的结论是「对齐度 **70–75/100，基本属实**」，而 [`项目总览.md`](../../项目总览.md) 后来写的是「**~90%**」。同一个东西，前后差 15–20 个百分点。

**准确的说法是**：功能**面**覆盖广——工具、斜杠命令、权限模式、上下文压缩、TUI、MCP、subagent 这些大类都做了；但每一项的**深度对齐是未验证的**。别把"有"当成"对齐"。

---

## 三、"生产就绪"的准确边界

"生产就绪"是一个**被过度使用**的词。准确边界是：

| 表述 | 是否成立 |
|---|---|
| 个人 / 小团队本地工具就绪 | ✅ 成立（日常自用没问题） |
| 企业生产环境就绪 | ❌ 不成立 |
| 可通过企业级安全审计 | ❌ 未经验证，是自我评价 |

文档里明确承认**不支持**：云端多用户、大规模并发、商业化部署（见 [`项目总览.md`](../../项目总览.md) 的"限制"一节）。所以"生产就绪"必须限定为**单机、单用户、本地**场景。

---

## 四、尚未做到 / 实现偏浅的部分

以下功能**有骨架但深度不足**，文档此前用「框架就位」一带而过，这里摆明：

| 功能 | 真实状态 |
|---|---|
| 真 LSP 长连接 | ❌ 未实现。`lsp.ts` 是 tsc 轻量诊断，不是 language server 协议 |
| cloud-gateway | 🟡 只是拼 URL，**不签** SigV4 / GCP 签名（源码注释自己承认） |
| speculation（投机预读） | 🟡 只在 grep/glob 后预测 Read，路径提取靠正则，默认关闭 |
| LLM 权限分类器 | 🟡 默认**关闭**，开启需额外 API 调用 + `--llm-perm-classifier`；关掉时只剩正则黑名单 |
| 多 Provider | ✅ 接入面广，但**未用真实第三方 API 做过大规模真机联调** |

**测试的边界**：1,117 个测试全部是单元 / 集成级，LLM 一律用 mock / stub，**没有**用真实 OpenAI / DeepSeek / Qwen / Anthropic API 跑过持续的真机联调。这意味着"模型真能听懂我的提示词并按预期调工具"这条链路，验证强度远低于测试数字本身暗示的水平。

---

## 五、安全防护的真实水平

文档用「企业级防护」描述安全，但真实情况是**分层、务实、但非企业级**：

1. **危险命令检测是正则黑名单**，可被绕过——`rm -rf` 能拦，`rm --recursive --force`、`find . -delete`、`python -c "import os; os.system(...)"` 拦不住。
2. 黑名单之上的 **LLM 分类器默认关闭**，且依赖额外模型调用。关闭状态下，安全底线就是那几条正则 + 阻断路径。
3. 阻断路径（`.env`/`.ssh`/`.git/` 等）**只拦 filePath 类工具**，拦不住 `bash` 里的 `cat .env`。

**好消息**：权限系统的**架构**是对的——`bypassPermissions` 也绕不过的"安全底线"、子代理继承父级审批、read-before-edit 等关键设计都真实落地了。但"企业级防护"这四个字，够不上。

## 六、已知技术债

这些是[`20260623-项目评审报告.md`](20260623-项目评审报告.md)里点过、目前仍在的：

- **循环依赖**靠 `lazy import()` 绕开（Task/Team 工具 ↔ tools.ts），说明模块边界有瑕疵。
- **两套工具注册路径并存**：`ToolRegistry` 与 `CORE_TOOLS` 数组需手动同步；`formatToolsForOpenAI/forLLM` 是死代码。
- **`any` 使用 81 处**，集中在 adapter 的类型断言。
- **`TODO` / `FIXME` 34 处**，有未收尾项。

都不影响日常使用，但"代码质量卓越 / 可维护性 8.5"这类分数，是在这些债之上的乐观估计。

## 七、文档数字会漂移

历史文档的计数与实际对不上，是**反复发生**的问题：

- 文档写"测试用例 1,079"，实测 **1,117**。
- 文档写"代码 27,156 行"，实测 **26,052 行**（src）+ 16,823 行（test）。

项目为此加了 `scripts/doc-sync.mjs`（`npm run docs:sync`）想根治，但截至本文档撰写，`项目总览.md` 的头部指标仍未同步到位。**读任何文档里的数字时，默认它可能偏旧；以 `npm test` / `npm run typecheck` 的实跑结果为准。**

## 八、一句话总结

> **代码是诚实的，文档曾经吹了。** 工程底子（类型安全、测试、核心抽象、安全底线）是真的，但"90% 对齐 / 生产就绪 / 企业级 / 5 星"这些结论是自我评价，需要打折。把定位放在「**高质量的架构研究与个人 / 小团队本地工具**」，它完全站得住；再往上，就是它还没做到、也未必打算做到的部分。
