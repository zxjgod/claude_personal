## 整体架构

```
CLI 入口 (cli.ts)  ──按 isTTY 分流──►  TUI 路径 (tui/run.tsx, Ink/React)
    │                                       │
    ├── 加载 .env / 配置 / CLAUDE.md         （两条渲染栈并存，见下）
    ├── 装配工具 (CORE_TOOLS) + MCP 工具 ──► 注册进 ToolRegistry
    ├── 构建系统提示 (system-prompt.ts，6 静态段 + 动态边界)
    │
    └── 主循环（行式 REPL 或 TUI 提交回调）
            ├── 斜杠命令 (commands.ts → commands/registry.ts) ── 本地处理
            │       └── 可返回 { prompt } 把生成的提示注回 agent loop
            ├── @file 引用展开 (file-refs.ts)
            └── Agent 循环 (agent-loop.ts) ── AsyncGenerator<LoopEvent>
                    │
                    ├── 模型调用 (ModelCaller，provider 无关)
                    │       ├── anthropic-adapter.ts（原生 Messages API + prompt cache）
                    │       └── llm-adapter.ts（OpenAI 兼容 + cloud-gateway 路由）
                    │
                    ├── 工具执行（并发分组 + 流式逐工具回传 + abort 竞速）
                    │       ├── PreToolUse hook → 工具级 checkPermissions → 系统级 checkPermission
                    │       └── PostToolUse hook
                    ├── 上下文压缩（snip 预修剪 → autoCompact 摘要）
                    └── speculation 预测性预取（grep/glob → 后台预读）
```

**核心抽象**：`ModelCaller` 用 `AsyncGenerator<StreamEvent>` 统一两个 provider 的输出，`agentLoop` 完全不感知 provider 差异（`types.ts`）。两个 provider 的 usage 口径不同，但都收敛到「不重复计入缓存 token」这一不变量（见 [LLM 适配层](#3-llm-适配层)）。

**两条渲染栈并存**：TTY 下走 `src/tui/`（Ink+React，`<Static>` 流式）；`--no-tui`/管道/CI 下走 `cli-*.ts`（行式 ANSI 重绘）。二者共享 `agent-loop`/`commands`/`markdown`/`terminal-width`/`effort`/`cli-errors`/`spinner-core`；输入框与工具卡片仍各自实现，spinner 的渲染层不同（行式 `Spinner` vs TUI `StatusLine`/`SpinnerGlyph`），但粒子字形、流光数学、计时/token 格式化共用同一份 `spinner-core.ts`。改任何终端 UX 都要检查两条路径，否则行为可能分叉。

## 一次请求的完整生命周期

下面是「用户敲一行字 → 屏幕出现回答」的端到端时序，标注每步对应的文件与关键函数。改一个功能前，先用它判断会牵动哪几个模块、按什么顺序。

```
① 输入捕获
   TTY:    tui/InputBox.tsx (useInput 编辑/补全) → tui/run.tsx onSubmit
   非 TTY: cli-input.ts (readline，续行/代码围栏) 或 cli-interactive.ts (raw-mode)

② 斜杠命令分流          commands.ts handleSlashCommand → commands/registry.ts 查表
   ├─ 纯本地命令：执行副作用 / 打印后 return（如 /clear /model /commit）
   └─ prompt 注入命令：返回 { prompt }，把生成文本当作用户输入继续（/review /recap /fork /onboarding）

③ @file 引用展开        file-refs.ts expandFileRefs（workspace 边界内读文件，越界/过大则记 note 跳过）

④ 系统提示（每轮）       cli.ts/tui 用 buildSystemPrompt 的结果 + 本轮 goal 拼成 turnSystemPrompt
                        （git 快照在会话启动时由 git-context 采集一次，注入动态段）

⑤ Agent 循环开始        agent-loop.ts agentLoop(messages, tools, callModel, modelConfig, opts)
   每一轮：
   5a. 上下文压缩       STEP1 snipContext 预修剪超大旧工具结果；仍超 150k token 才 autoCompact LLM 摘要
   5b. 模型流式调用     callModel → StreamEvent（text_delta → tool_use → done）
                        ├─ anthropic-adapter（cache_control 断点 + 精确 usage）
                        └─ llm-adapter（stream_options.include_usage + tool_call 分片按 index 累积）
   5c. 工具执行         按 tool.isConcurrencySafe() 分组：并发组并行 / 其余串行，按 index 保序
        对每个工具：PreToolUse hook → 工具级 checkPermissions → 系统级 checkPermission
                    （4 模式 + 危险正则 + 阻断路径 + 可选 LLM 分类器 → askUser）
                    → tool.call() → PostToolUse hook → yield tool_result（逐个回传）
        speculation：上一轮 grep/glob 的结果触发后台预读，本轮 Read 命中缓存即时返回
   5d. 错误处理         handleModelError：429 / context_length / auth / timeout 四类有界重试
   循环直到模型不再发起工具调用或达 maxTurns(50)

⑥ 事件渲染             LoopEvent 逐个消费
   TTY:    tui/run.tsx → TuiStore 变更 → App.tsx (useSyncExternalStore) 重渲染
           text_delta 经 stream-buffer.ts 合批约 30fps；StatusLine/SpinnerGlyph 自带 interval 只重绘状态叶子
   非 TTY: cli.ts → cli-renderer.ts (StreamingRenderer 块缓冲) + cli-spinner.ts

⑦ 持久化与留痕         tool_results / done 事件触发：
   session-memory.ts（可 resume 的 live 快照 .json，串行原子写）
   session-transcript.ts（append-only 审计流 .transcript.jsonl）
   session-stats.ts（token/成本累计）  telemetry.ts（可选本地遥测，默认关）
```

四类「会话状态」是进程内内存、按 `sessionId` 隔离、重启即失：`read-tracker`、`change-tracker`、`todo`、`team`/`worktree`/`cron` 的状态 Map。只有 `session-memory` / `session-transcript` / `memories.jsonl` / `telemetry` 真正落盘。

## 模块清单

> 每个模块给出：**职责**（一句话）、**关键导出**、**不变量/注意**（改动时不能破坏的约束）。验证命令、故障模式、影响半径见 [`模块维护方案.md`](./模块维护方案.md) 的同名维护卡。

### 1. 入口与 CLI 层

#### `src/cli.ts`（879 行）
- **职责**：CLI 进程主入口 —— 加载 `.env`/配置/CLAUDE.md、装配工具+MCP+系统提示、按 `isTTY` 分流到 Ink TUI 或行式 REPL，并在 REPL 路径里逐 `LoopEvent` 驱动渲染、持久化、转录、遥测、权限/提问回调。
- **关键导出**：无具名导出（shebang + `bin` 自执行 `main()`）。内部关键单元：`loadConfig`/`getPermissionMode`/`loadClaudeMd`/`makeCommandContext`/`main`。
- **不变量/注意**：
  - TTY 路径会 `return`，**根本不执行**后面的 REPL/权限菜单/cleanup 注册 —— 给 REPL 加的逻辑若要在 TUI 下生效，必须同时改 `tui/run.tsx`。
  - `cleanup()` 幂等，且兼当 `SIGTERM`/`unhandledRejection`/`uncaughtException` 的兜底 —— 新增长生命周期资源（LSP/MCP/子进程）必须在此释放，否则退出留孤儿。
  - spinner 与 `cli-renderer` 共用 `stdout`：渲染前必须先 `spinner.stop()` + `flush()`，否则 `\r` 行与正文互相覆盖。
  - 系统提示里的 git 快照只在启动时采集一次，会话中切分支不会刷新。

#### `src/index.ts`（134 行）
- **职责**：作为「库」被外部 import 时的**选择性** barrel（不是全量公共 API）。
- **关键导出**：re-export `types.*`、`agentLoop`/`autoCompact`、`handleSlashCommand`/`COMMANDS`、`CORE_TOOLS` 及各工具、`HookRegistry`、`ToolRegistry`/`createTool`、`anthropicCaller`、`createModelCaller`、`MCPManager`、`PersistenceManager` 等。
- **不变量/注意**：手维护的白名单，**已漏掉约一半模块**（team/tools-team/tools-m9/session-stats/telemetry/记忆三件套/effort/skills/markdown/cli-* 等）。`cli.ts` 不经它（直接 import 具体模块），改它只影响「作为库引用」的场景。

#### `src/cli-input.ts`（81 行）
- **职责**：非 TTY/管道场景的 readline 包装 —— EOF 安全的 `askQuestion`/`readInput`，支持反斜杠续行与 ``` 代码围栏多行聚合。
- **关键导出**：`createCliInputReader(rl)` → `{ askQuestion, readInput, isClosed }`。
- **不变量/注意**：只管行式输入，不碰 raw mode/光标（那是 `cli-interactive`）。续行靠 `endsWith('\\')`，CRLF 管道下 `\r` 会让续行失效（Windows 已知坑）。

#### `src/tui/cli-interactive.ts`（原 `src/cli-interactive.ts`，571 行）
- **职责**：TTY 专用 raw-mode 交互层 —— 带边框输入框 + `/` 命令补全下拉、权限三选菜单（Yes/Always/No）、单/多选提问菜单，全用 ANSI 原地重绘。
- **关键导出**：`createRawInputReader(opts)`、`promptPermissionMenu(opts)`、`promptSelectMenu(opts)`；类型 `CommandInfo`/`PermissionChoice`/`SelectMenuOption`。
- **不变量/注意**：命令列表由 `cli.ts` 以 `CommandInfo[]` **注入**（不直接 import `commands`）。绘制走注入的 `output`（默认 `stdout`），测试靠这个注入，别改成直接引用 `process.stdout`。权限菜单是安全闸口的 UI，返回值错误会让用户误授权。

#### `src/tui/cli-renderer.ts`（原 `src/cli-renderer.ts`，275 行）
- **职责**：把终端呈现逻辑从 `cli.ts` 剥离 —— 流式 assistant 文本的块缓冲 markdown 渲染、欢迎屏、工具开始/结果（●/⎿，长输出折叠）、子代理活动、文本版权限提示框。
- **关键导出**：`StreamingRenderer` 类、`renderWelcome`、`renderToolStart`、`renderToolResult`、`renderSubAgentActivity`、`renderPermissionPrompt`。
- **不变量/注意**：块缓冲有延迟语义（测试里 `write` 后须 `flush` 再断言）。仅行式 REPL 用它，TUI 自渲染。依赖 `markdown` + `terminal-width` + `types`。

#### `src/tui/cli-spinner.ts`（原 `src/cli-spinner.ts`，169 行）
- **职责**：行式 REPL 的「思考中」状态行渲染器 —— 在 `spinner-core.ts` 共享原语之上，用 chalk 输出粒子字形 + 颜色 shimmer + 已用秒数 + token，`\r` 原地重绘；非 TTY 自动降级为不动。
- **关键导出**：`Spinner` 类、以及从 `spinner-core.ts` re-export 的 `SPINNER_VERBS`、`computeShimmerSegments`、`formatDuration`、`formatTokens`。
- **不变量/注意**：依赖 `cli.ts` 在所有路径调 `stop()` 清 timer（否则可能吊住事件循环）。TUI 不直接用 `Spinner`，而是用 `StatusLine`/`SpinnerGlyph`；两端共享 `spinner-core`。当前粒子帧集按偏好移除了 `✳`：`· ✢ ✶ ✻ ✽`。

#### `src/cli-errors.ts`（约 90 行）
- **职责**：把 provider/SDK 错误精简为终端友好的一句行动建议，**绝不打印 headers/巨型请求对象或泄漏密钥**。
- **关键导出**：`formatCliError(error)`。
- **不变量/注意**：REPL 与 TUI 共用的唯一错误文案出口。与 `llm-adapter` 的 `isAuthError`/`isRateLimitError`/`isContextLengthError` 是**两套独立判断**（一套控制流、一套展示），改一套不会自动同步另一套。

### 2. Agent 循环核心 + 上下文优化

#### `src/agent-loop.ts`（509 行）—— 项目心脏（已拆分）
- **职责**：驱动「模型流式调用 → 工具并发/串行执行 → 再调用」的异步生成器，编排四类错误有界重试、abort 竞速、speculation、Pre/PostToolUse hook；压缩逻辑已拆到 `auto-compact.ts`/`error-recovery.ts`。
- **关键导出**：`agentLoop`（async generator，产出 `LoopEvent`）。`autoCompact` 现从 `src/auto-compact.ts` 导出（供 `commands/compact.ts` 复用）。
- **不变量/注意**：
  - 工具执行结果按 `done.index` 回填到 `new Array(len)`，并发组与串行组必须覆盖全部 index，否则 STEP6 拼 tool 消息时 `toolResults[i]` 抛错。
  - `findSafeSplitIndex` 防「孤儿 tool result」（摘要后尾部以 tool 消息开头会被 provider 拒绝）—— 有专门回归测试 `compaction.test.ts`。
  - `messages` 是「就地 push + 压缩时整体重赋值」混用：压缩后调用方持有的旧引用不再同步，读最终历史要从 loop 外的来源拿。
  - 改 `LoopEvent` 形状会同时牵连 `cli.ts` 与 `tui/run.tsx` 两套渲染，以及 task-tool/team 子代理消费。

#### `src/context/context-snip.ts`（原 `src/context-snip.ts`，89 行）
- **职责**：autoCompact 之前的廉价、近无损预压缩 —— 纯函数式就地修剪「庞大且陈旧」的工具结果为 head+tail+`SNIP_MARKER`，保护最近 `keepRecent`(10) 条与所有非工具消息。
- **关键导出**：`snipContext`、`SNIP_MARKER`、类型 `SnipOptions`/`SnipResult`。
- **不变量/注意**：幂等（含 marker 不二次修剪）；只处理 `string` 类型的工具结果（结构化数组 content 会被跳过）；纯函数，未修改的消息按引用透传。唯一消费者是 `agent-loop` STEP1。

#### `src/speculation.ts`（260 行）
- **职责**：预测性工具预取 —— grep/glob 返回路径后排名、按候选规模缩放上限、过滤已读，后台并发预读 top-N 文件并缓存，下轮 Read 命中即时返回；附 hit/miss/wasted 统计。
- **关键导出**：`SpeculationCache` 类（`prefetch`/**`take`**/`getStats`/`isEnabled`）、`rankPaths`、`predictReads`、`effectiveCap`、`specKey`、`formatSpeculationLine`。
- **不变量/注意**：`predictReads` 造的键 `{filePath}` 必须与真实 Read 的 `input` 字段名/取值一致才命中（三处强耦合：predictReads / agent-loop 命中读取 / readFiles 去重）。**默认开启**，`--no-speculation`/`CCR_SPECULATION=0` 关闭。Windows 绝对路径盘符冒号是已知局限（本项目工具多输出相对路径，影响有限）。

### 3. LLM 适配层

#### `src/llm-adapter.ts`（335 行）
- **职责**：多 provider 客户端适配 —— 内部消息↔OpenAI 格式转换、OpenAI 兼容流式 caller、`createModelCaller` 工厂按 provider 选 anthropic/openai 路径、错误分类、`resolveProviderConfig`（含云网关与 effort 解析）。

## 关键机制详解

### 并发与执行模型

- **工具分组**：`agent-loop.executeToolCalls` 按 `tool.isConcurrencySafe()` 把一轮的工具调用分成「并发组」（并行 `Promise.race` 推进）与「串行组」，结果按调用 `index` 回填以保持历史顺序。判据只看工具自报的并发安全标记，**不看输入是否写冲突** —— 安全性押在工具实现上。`BashTool` 被显式标为非并发安全。
- **abort 竞速**：并行路径用 `Promise.race([工具, abortPromise])`，任一工具永不 settle 时 abort 也能打断；仍 pending 的调用 yield aborted 占位结果以保证结果数组完整。这是 Ctrl+C 能生效的关键（与 Bash 进程树杀配合）。
- **子代理并发**：`task-tool` 用进程内信号量（默认 3，`TASK_MAX_CONCURRENCY`）限流，防 fan-out 打爆 provider 速率。
- **speculation**：上一轮 grep/glob 结果触发后台预读，缓存单次消费（`take` 后 delete）、每 loop run 重建（非持久 LRU）。

### 上下文优化两级管线

```
estimateTokens（char/4 粗估，忽略图片/结构开销）
   │ 超 autoCompactThreshold(150_000)？
   ├─ STEP1  snipContext  预修剪超大旧工具结果（保护最近 10 条 + 非工具消息，幂等）
   │           回收够 headroom → 本轮直接继续，省下昂贵的 LLM 摘要
   └─ 仍超阈值 → autoCompact  LLM 摘要（保留尾部 TAIL_SIZE=20，findSafeSplitIndex 防孤儿 tool）
```
两套保护窗口各算各的（snip 的 `keepRecent=10` 与 autoCompact 的 `TAIL_SIZE=20` 不对齐）。

### 错误处理与重试策略

`handleModelError` 按错误类型分流，**有界重试**：

| 错误类型 | 判定 | 处理 |
|---|---|---|
| 429 限流 | `isRateLimitError` | `sleep(retryAfter)` 后重试，与超时共享 `MAX_RATE_LIMIT_RETRIES=3` 预算 |
| 上下文超限 | `isContextLengthError` | 触发 `autoCompact` 再重试，`MAX_CONTEXT_LENGTH_RETRIES=3` |
| 网络抖动/超时 | timeout/ECONNRESET | 归入 rateLimit 预算重试 |
| 鉴权 401/403 | `isAuthError` | 立即终止（不重试） |
| 用户 abort | — | 永不重试 |

工具执行失败降级为 `ToolResult.error`（不崩溃）；provider 错误经 `cli-errors.formatCliError` 脱敏展示。

### 安全闸门与工具执行管线顺序

每个工具调用在 `agent-loop.executeSingleTool` 里按固定顺序过闸：

```
runPre (hook 可阻断/改写 input)
  → tool.checkPermissions (工具级硬策略)
  → checkPermission (系统级 4 模式七步：
       1 isReadOnly 放行 → 2 plan 模式阻断非只读
       → 3 isBlockedPath → 4 dangerousPattern(+可选 LLM 分类器)
       → 5 bypassPermissions → 6 acceptEdits → 7 默认 askUser 确认)
  → tool.call()
  → runPost (hook 可替换 result)
```
顺序即安全语义：`runPre` 必须在权限前；`isBlockedPath` 与 `dangerousPattern` 是 bypass-immune 安全地板，必须在 `bypassPermissions` 前执行；`acceptEdits` 在 dangerous 之后（危险 edit 仍确认）；分类器 ALLOW≠放行、BLOCK 前置短路。M38 后 TUI 的 Shift+Tab 只改变实时 `permissionMode`，每次工具检查前由 `ToolContext.getPermissionMode()` 刷新，不允许绕开这条管线。
