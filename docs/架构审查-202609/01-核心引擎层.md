## 2. 数据流：一次 query 的完整生命周期

入口有三处：交互式 REPL（`cli-repl.ts:315`）、TUI（`tui/run.tsx`）、非交互 `-p` 模式（`cli.ts:421`）。均把**同一个 messages 数组**（调用方持有、自动持久化）交给 `agentLoop`。

### 循环初始化（agent-loop.ts:104–258）
- 组装 `baseContext: ToolContext`（权限模式、hooks、collapseStore、`getParentMessages` 等，L181–204）；
- 创建三个跨轮状态容器：`SpeculationCache`（L224）、`readFiles` 集合（L225）、`StreamingToolExecutor`（L227–246，注入的 runner 就是 `executeSingleTool` 的偏应用，保证早启动与正常执行走**同一条**权限/hook 管线）；
- 启动 prefetch promise（L254–256，输入为 `latestUserText`）；
- `replaceMessages()`（L137–139）用 `splice` 原地替换，**刻意保持数组身份**——这同时是 CLI 自动保存和 `prompt-cache.ts` WeakMap scope 的前提。

### 每轮 while 循环（L261–848）

**STEP 1 上下文准备（L269–332）**：`estimateContextTokens` = 上次 usage 基线 + 增量估算（L869–875，避免每轮全量重估）→ `prepareCheapLayers` 跑层1→1.5→2→3（仅在**超过阈值**时才动裁剪层，阈值以下保持字节稳定以护住 prompt cache）→ 若仍超阈值（默认 150k，L115）触发 `autoCompact`（层5，PreCompact/PostCompact hooks 包裹，fast model 优先、失败降级主模型、再失败**保留原历史**继续走 L315–322）；阈值被禁用时还有 200k 硬限兜底（L323–332）。

**STEP 2 流式模型调用（L334–595）**：先注入 prefetch 附件和上一批工具的 fast-model 摘要（都是一次性 `role:"system"` 消息追加，L337–352）。然后消费 `safeCallModel` 的事件流：
- `text_delta` → 透传 UI + 累积 buffer；
- `thinking` → 仅 UI 显示（签名块在 done 才到）；
- `tool_use` → 记入 `toolCalls`；**若 `rawArguments === undefined`（即参数完整可解析）同时喂给 `streamExecutor.add()` 早启动**（L399–400）；
- `done` → 记 usage、更新 `usageBaseline = {promptTokens: input_tokens, messageCount: windowAtCall}`、`recordOutput` 进预算；
- `error` → 交给 `handleModelError`：retry/retry_transient（退避睡眠后重打）、compact_and_retry（当场压缩再重打）、abort（先尝试 fallback 模型链 L508–521，单调推进 `fallbackIndex`）。
- 重试边界有 `CCR_RETRY_CONTINUE=1` 实验路径（L573–589）：非 Anthropic、纯文本 ≥1000 字符时提交半截输出并注入"从断点继续"指令，省一次全量重生成。

**STEP 3 无工具调用 → 结束判定链（L597–720）**，顺序为：持久化 assistant 消息（含签名 thinking 块）→ Stop hook（`blockingError` 注入后续轮）→ 输出预算 auto-continue nudge → `finish_reason === "length"` 截断恢复（M40，注入 nudge 续写）→ 背景完成通知注入（M41，≤10 次连续通知续轮）→ 队列输入注入（type-ahead，每条开一个 checkpoint 边界）→ 全部落空则 `yield done` 并 `return terminal("completed")`。

**STEP 4–6 工具执行与回写（L722–847）**：assistant(tool_calls) 入史（thinking 块必须随行，否则 interleaved-thinking 下 API 400）→ `executeToolCalls` 按批次执行（详见 §3），逐个 `yield tool_result`；异常时合成错误结果，`finally` 中**无条件**为每个 tool_use 配对一条 tool 消息（`backfillMissingToolResults` 兜底），保证 API 不变量 → 对 grep/glob 结果做投机预取（L787–798）→ 启动本批工具的 fast-model 摘要（下轮 STEP 2 消费）→ 工具结果中的图片作为 user 消息附加 → 合并队列输入与背景通知 → `turnCount+1` 进入下轮。

### 压缩触发时机汇总
| 机制 | 时机 | 位置 |
|---|---|---|
| 层1 边界丢弃 | 每轮 STEP 1（有摘要边界时物理丢弃前史） | context-pipeline.ts:80 |
| 层1.5/2/3 裁剪驱逐 | 每轮 STEP 1，仅当估算 > 150k 阈值 | context-pipeline.ts:380–419 |
| 层5 autoCompact | 便宜层跑完仍超阈值；或 provider 报 context_length 后 compact_and_retry | agent-loop.ts:285, 461 |
| 时间型 micro-compact | **会话加载时**（闲置 ≥60min 才清），循环内不跑 | cli-session.ts:89,144 |

### 缓存策略
真正的 cache_control 断点在 adapter 层：system 稳定前缀（`DYNAMIC_BOUNDARY` 之上）、最后一个工具 schema、最后一条消息的最后一个 block 各打一个 ephemeral 断点（anthropic-adapter.ts:51–66, 232–236, 246–257）。`prompt-cache.ts` 只做**断裂检测**：调用前哈希 diff（scope=messages 数组身份），调用后 cache_read 降幅 >5% 且 >2000 → 归因输出（仅 `DEBUG_PROMPT_CACHE=1` 时打印，anthropic-adapter.ts:469–475）。便宜压缩层"阈值以下不动历史"正是为了保住 cache 前缀字节稳定。

## 3. 关键设计决策

**并行工具执行**（tool-executor.ts）：数据驱动的保守判定——解析参数后问 `tool.isConcurrencySafe(input)`，解析失败/谓词抛错一律视为不安全（L68–77）。贪心分批保序：连续安全调用并成一批并行，任何不安全调用独占串行批，`[read, write, read]` → 三个批次，第二个 read 不会越过 write（L86–98）。并行批用自研 `all()`（utils/generators.ts:16–60）做有界并发合并（默认 10，`CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` 可调），**按完成序** yield，agent-loop 按 index 回填数组再按调用序写入历史。abort 用单个共享 `abortPromise` race 整个批次（修过每迭代泄漏 listener 的 P2 bug，L478–513），中断后为未 emit 的调用合成 aborted 结果。每个工具调用有 watchdog：`combineAbortSignals(parent, timeout)`，默认 5min、上限 30min，超时抛 `ToolWatchdogTimeoutError`（只是工具失败，不取消父循环，L119–156）。

**流内早启动**（streaming-tool-executor.ts）：刻意做成"薄缓存"而非第二套执行器——`add()` 复用循环注入的 `executeSingleTool` runner（权限/hook/审计全走），STEP 5 `take(id)` 命中即取，未命中零行为变化；`clear()` 通过 `CancellationScope` 级联取消。这是对真实 CC 的**原创扩展**（真实 CC 等流完全结束才执行工具）。

**压缩策略**：五层从轻到重（见上表），核心权衡是"便宜层不读内容、只在超阈值时动历史"以兼顾 prompt cache。autoCompact 用 `findSafeSplitIndex` 保证不拆 tool_use/tool_result 对（auto-compact.ts:15–30），摘要失败**宁可保留原历史**也不提交空摘要（L89–93）——因为空摘要会永久摧毁旧消息。时间型 micro-compact 与计数型正交：前者在会话恢复时清（resumed 会话开局更便宜），后者在循环内按数量清。

**投机执行三件套（M36"隐藏延迟"）**：模型流式输出的 5–30s 被当作免费算力窗口——① `speculation.ts`：grep/glob 出路径 → 排序 + 动态上限（候选越多预取越少，`effectiveCap` L107–112）→ 后台 Read；真实调用在 `executeSingleTool:343` 命中缓存。② `prefetch.ts`：memory/skill 关键词排名，注入下一轮。③ `tools/summary.ts`：fast model 摘要上一批工具输出，下轮注入。三者都是 fire-and-poll、失败静默。

**错误恢复**：分类决策集中在纯函数 `handleModelError`，三种重试各自独立预算（3/3/3），429 与瞬时错误都用指数退避+20% 抖动（429 上限 60s、瞬时上限 30s）；`retry` 通知回调让 UI 显示倒计时。fallback 模型链是单调的（每个 fallback 每会话最多试一次），且明确排除 401/403/429/abort（账户级错误换模型无意义）。压缩失败不杀会话，靠 context_length → compact_and_retry 二次兜底。

## 4. 耦合与弱点

### 高危（正确性 bug，有明确证据）

**H1. Anthropic 路径的 usage 基线漏加 cache_read → 上下文被系统性低估，压缩永不触发。**
`anthropic-adapter.ts:455–464` 的注释明说："input_tokens 现在**不含**缓存 tokens……loop 可以用 input + cache_read 估算 live context"。但 `agent-loop.ts:409` 只取 `event.usage.input_tokens` 作 `usageBaseline.promptTokens`，从未加 `cache_read_input_tokens`（全文件 grep 无 cache_read）。缓存命中良好的会话里，150k 的真实 prompt 报出来的 input_tokens 可能只有几 k → `estimateContextTokens`（L869–875）严重低估 → STEP 1 的阈值判断和便宜层全部失效 → 一路撞到 provider 400。OpenAI 路径无此问题（llm-adapter.ts:250–262 的 prompt_tokens 含缓存），**两个 provider 语义不一致**。

**H2. Anthropic 的 context 超限错误消息匹配不上 `isContextLengthError` → compact_and_retry 在主 provider 上是死路径。**
`error-recovery.ts:48` 只匹配 `"context_length"` / `"maximum context"`（OpenAI 措辞）。Anthropic 实际消息是 `"prompt is too long: 216617 tokens > 200000 maximum"`——两个子串都不含。于是 H1 撞墙后，恢复决策走"未知错误 → abort"，`isFallbackableModelError`（L58–66）对 400 返回 true → 白白烧掉整条 fallback 模型链（每个都因同样超长的上下文失败），最后以 `model_error` 终止而非压缩重试。项目内部其实知道这个措辞：`tui/i18n.ts:545` 匹配了 `"too long"`，但恢复逻辑没有。`llm-adapter.ts:334` 还有一份**复制粘贴的** `isContextLengthError`，两份将来必然漂移。H1+H2 叠加是主 provider 上的复合故障链。

**H3. 流内早启动破坏同一条 assistant 消息内的工具顺序语义。**
`agent-loop.ts:399–400` 对每个安全 tool_use 无条件 `streamExecutor.add()`，**不检查同流中是否有更早的不安全（变更型）调用**。场景：模型在同一消息里发 `Write(f)` + `Read(f)`——Write 要等 STEP 5 串行批执行，Read 却在流式期间就被早启动，读到**写入前**的旧内容，STEP 5 `take(id)`（tool-executor.ts:426–427）把这份过期结果按正确顺序回给模型。`partitionToolCalls` 精心保序（注释里 `[read, write, read]` 的例子），早启动却从旁边绕过了这个保证。`Bash(mkdir/sed -i)` + `Read` 同理。

**H4. SpeculationCache 无失效机制 → 跨轮陈旧读。**
`SpeculationCache` 活在整个 agentLoop run（多个模型轮）里，`pending` 条目只在 `take()` 时消费，**没有任何针对文件变更的 invalidate/TTL**（grep speculation.ts 无 invalidate/clear）。场景：轮1 grep → 预取 Read(foo.ts)；轮3 模型 Edit(foo.ts)；轮4 模型 Read(foo.ts) → `specKey` 命中，返回**编辑前**内容。`readFiles`（agent-loop.ts:225）只防重复预取，不防陈旧。模型基于过期文件内容继续 Edit 会直接产生 wrong-string-match 或更糟的静默错改。

**H5. 投机预取绕过 PreToolUse hook 与权限层。**
`speculation.ts:228` 直接 `tool.call(pred.input, context)`，只靠 `isReadOnly && isConcurrencySafe` 把关（L225）。虽然结果要等 `executeSingleTool` 里 hook/权限跑完才会被消费（tool-executor.ts:323–354，被拒时缓存内容不入模型），但**磁盘读取这个副作用本身已经发生**——配置了"拒读敏感路径"PreToolUse hook 或沙箱策略的用户，其拦截在预取路径上被绕过（读发生了，只是结果被丢弃）。与早启动执行器"复用完整管线"的严谨设计形成鲜明反差。

### 中危

**M1. 退避睡眠不可取消。** `error-recovery.ts:93/141` 的 `sleep()` 不接 abortSignal——429 退避最长 60s+抖动，期间 Ctrl+C 无响应（循环卡在 `await handleModelError` 里）。

**M2. 5xx/529 不重试。** `handleModelError`（L72–147）对 500/502/503/529（Anthropic overloaded）没有瞬时重试分支，直接落入 abort → fallback 链。真实 CC 会对 overloaded 退避重试。一次抖动就放弃主模型过于激进。

**M3. `err?.retryAfter`（error-recovery.ts:86）是死代码。** 全仓 grep 只有这一处——没有任何 adapter 在错误对象上设置 retryAfter，Anthropic SDK 的 Retry-After header 也没被解析。429 退避永远从 5s 基线起。

**M4. 重试计数器跨整轮循环累积、成功后不清零**（agent-loop.ts:447–460 只加不减）。一个长会话累计吃过 3 次 429 后，第 4 次直接 abort——而真实 CC 的重试预算是按请求序列计的。

**M5. fallback 换模型后 `baseContext.modelConfig` 不同步。** `agent-loop.ts:516` 重新赋值了 `modelConfig` 局部变量，但 L188 构造 baseContext 时捕获的是旧对象——之后 Task/Team 子代理仍用已被放弃的主模型。`effectiveSystemPrompt`/effort 参数也没按新模型能力重算。

**M6. grep 路径抽取在 Windows 绝对路径下失效。** `speculation.ts:157` 的 `^([^:]+):\d+:` 遇到 `D:\proj\src\a.ts:42:` 只会抽出 `"D"`。本项目就跑在 Windows 上；相对路径输出可用，绝对路径输出时投机预取全部打空（无害但功能归零）。

**M7. 每轮注入的 system 附件永久留在历史里。** prefetch 附件（L344）和工具摘要（L350）作为 `role:"system"` 消息 push 后**从不摘除**，长会话积累几十条过期的 skill/memory 提醒，既占上下文又可能误导模型（真实 CC 的 system-reminder 不这样持久堆积）。

**M8. `evictionStub` 对模型撒谎（跨轮）。** stub 承诺 "may be recoverable via RestoreContext"（context-pipeline.ts:42），但 `CollapseStore` 每次 agentLoop 调用新建（agent-loop.ts:178），REPL 下即每个用户轮一个——上一轮被驱逐内容的 stub 留在历史里，指向一个已死的 store，模型调用 RestoreContext 必然 miss、白烧一轮工具调用。

### 低危 / 设计债

- **L1. 死状态**：`LoopState.transition` 只写不读；`totalTokens`（agent-loop.ts:412）累积后无任何消费者；`turnOutputBudget`（M32）在 REPL/TUI 生产路径均未传入（grep 证实），整个 token-budget 模块实际是死特性，只有 `finish_reason==="length"` 恢复复用了它的 nudge 文案（而该文案"如果完成了就明说"并不贴合截断续写场景）。
- **L2. 双重 microcompact**：`prepareCheapLayers` 在 context-pipeline.ts:403 和 411 连跑两次 `microcompact`，agent-loop 从不传 `opts.micro`，第二次对幂等 stub 是纯 no-op——重构残留。
- **L3. 层1.5 的 32 位 FNV-1a 碰撞即静默数据丢失**：`dedupeToolResults`（context-pipeline.ts:135–142）碰撞时把真实内容替换成指向**不同内容**的 "duplicate of" 指针，无校验。概率低但后果是内容级错误。
- **L4. `context.permissionMode` 就地变更**（tool-executor.ts:311）：baseContext 被并行工具共享，属良性竞态但违反自己声称的"LoopState 整体重写"纪律。
- **L5. 分层违规**：核心引擎 `agent-loop.ts:36` import `./tui/effort.js`（effort 是模型配置关切，放错了目录）；还 import `tools/summary.js`、`checkpoint.js`——循环对 UI 层和工具层都有直接依赖。
- **L6. 硬编码遍地**：150k/200k 阈值与模型无关（provider-profiles 无任何 context-window 元数据，grep 证实）；team.ts 用另一个阈值、workflow.ts 用 50k；`"claude-opus-4-8"` 写死在 adapter；`MAX_NOTIFICATION_CONTINUATIONS=10`、TAIL_SIZE=20、头600/尾400、2000 tokens/5% 断裂阈值等均为魔数。环境变量开关散落 6+ 个模块（CCR_*、CLAUDE_CODE_*、DEBUG_PROMPT_CACHE）。
- **L7. 行为分叉**：REPL 路径没传 `drainQueuedInput`（只有 tui/run.tsx:204 传了），非 TUI 用户没有 type-ahead 注入。
- **L8. `estimateTokens` 的图片公式**（token-estimator.ts:130–132）`85 + data.length*4/750` 把 base64 长度当像素数近似，量纲混乱，大图误差可达数倍。

### 与真实 Claude Code 的差距
1. 真实 CC 的压缩阈值来自**模型上下文窗口**（~92% 触发）并用 countTokens API 校准；这里是写死的 150k + 纯启发式估算（且 H1 让估算在 Anthropic 上失真）。
2. 真实 CC 的 compaction 摘要更结构化（含文件状态快照、8 节式提纲），这里是 5 点式自由摘要（auto-compact.ts:124–132），恢复后模型对"哪些文件改成什么样"的掌握更弱。
3. 真实 CC 会对 429 解析 Retry-After、对 529 overloaded 重试；这里 M2/M3 两条都缺。
4. 早启动（H3）与投机读（H4/H5）是原创特性，真实 CC 没有对应物——收益真实，但引入的 ordering/staleness 风险也是真实的。
5. 真实 CC 的 microcompact 由上下文压力驱动；这里的时间型 micro-compact 只在会话加载触发（闲置 60min），运行中的长会话永远等不到它。

## 5. 可升级点（按优先级）

1. **修复 usage 基线**（agent-loop.ts:409）：`promptTokens = input_tokens + (cache_read_input_tokens ?? 0) + (cache_creation_input_tokens ?? 0)`，或让 adapter 额外输出一个 `context_tokens` 字段统一两 provider 语义（llm-adapter.ts:250–262 已含缓存，注意别双计）。这一条修好，整个压缩体系才在 Anthropic 路径上生效。
2. **补齐 context 错误识别**（error-recovery.ts:48, 99–101）：加入 `"prompt is too long"`、`"too many tokens"` 等 Anthropic 措辞（可对齐 tui/i18n.ts:545 已有的模式）；删除 llm-adapter.ts:334 的重复实现，统一 import error-recovery。
3. **早启动加"前序屏障"**（agent-loop.ts:399–400）：流式消费中维护 `sawUnsafeCall` 标志，一旦本条消息出现过非 concurrency-safe 的 tool_use，后续安全调用不再 `add()`；即可恢复 `partitionToolCalls` 的顺序语义，改动约 5 行。
4. **给 SpeculationCache 加失效**：最简方案是每次变更型工具（write/edit/multi_edit/bash）执行成功后 `specCache.clear()`（或按 `readFiles` 中路径做 key 级失效）；在 tool-executor.ts:359–367 记录 readFiles 的位置顺手做。同时给 pending 条目加 TTL（如 30s）。
5. **投机预取走 hook 管线**（speculation.ts:225–236）：至少跑 `hooks.runPre` 的 block 判定再决定是否发起后台读；或把预取执行改为复用 `executeSingleTool`（与 streaming-tool-executor 同一模式），消除策略绕过。
6. **可取消的退避**（error-recovery.ts:40–42）：`sleep(ms, signal)` 用 `combineAbortSignals` 实现，`handleModelError` 多收一个 `abortSignal` 参数；同时给 5xx/529 增加瞬时重试分支，并解析 Anthropic SDK 错误的 `headers['retry-after']` 填到 `err.retryAfter`。
7. **成功调用后清零重试计数**（agent-loop.ts:404–419 的 done 分支）：`rateLimitRetries/transientRetries` 归零，`contextLengthRetries` 可保留（防压缩死循环）。
8. **模型感知的阈值**：在 provider-profiles 增加 `contextWindow`，`autoCompactThreshold` 默认改为 `contextWindow * 0.85` 之类的派生值，替换 agent-loop.ts:115–116 的魔数；team.ts:243 / workflow.ts:94 的私有阈值一并收敛。
9. **fallback 后同步 baseContext**（agent-loop.ts:516）：换成 `baseContext.modelConfig = {...}` 或让 baseContext 持 getter；并为模型切换新增专用事件类型，别再复用 `compacted`（L517 现在 UI 会把它渲染成一次压缩）。
10. **附件生命周期管理**（agent-loop.ts:337–352）：prefetch/摘要附件改为在下一轮注入后从 messages 中摘除（或用带标记的临时消息，在 STEP 1 由层1 清理），防止跨轮堆积。
11. **CollapseStore 与 stub 语义对齐**：要么把 store 提升到 session 级（跨 agentLoop 存活），要么 stub 文案在 store 死亡后不再承诺可恢复（context-pipeline.ts:36–43）。
12. **小清理**：删掉 context-pipeline.ts:410–418 的第二次 microcompact；删除或接线 `LoopState.transition`/`totalTokens`；把 `tui/effort.ts` 移到 `src/` 顶层解除核心→TUI 依赖；`speculation.ts:157` 的路径正则改为兼容盘符（如 `^([A-Za-z]:[\\/][^:]+|[^:]+):\d+:`）；dedupe 的 FNV-1a 换成 64 位或碰撞时二次比对长度。

## 总体评价

这是一套注释密度和工程自觉性都很高的复刻——保序分批、tool_use/tool_result 配对兜底、压缩失败不毁历史、checkpoint 边界语义、缓存前缀稳定性等都考虑到了，且测试覆盖可观（agent-loop.test.ts 2256 行）。但它的最关键路径（Anthropic provider 上的上下文计量与超限恢复）存在 H1+H2 的复合缺陷，两个原创加速特性（早启动、投机读）各带一个真实竞态（H3/H4）。这五个问题修复成本都不高（每项 5–50 行），修完后核心引擎的可信度会上一个台阶。
