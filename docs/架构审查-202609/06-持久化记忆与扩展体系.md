## 1. 会话持久化

### 1.1 存储格式与位置

所有状态都放在 **工作区内** `<workspace>/.claude/`（`src/workspace-config.ts` 的 `ccrPath()`），刻意不读官方 Claude Code 的 `~/.claude`（`src/mcp/index.ts:891` 注释明确写了 "never read official Claude Code locations"）。双轨存储：

| 存储 | 格式 | 位置 | 职责 |
|---|---|---|---|
| **会话快照** | 单个大 JSON（非 JSONL），`SESSION_FORMAT_VERSION = 3` | `.claude/sessions/<id>.json` | 完整 `Message[]` + 元数据，供 resume |
| **事件转录** | **JSONL** 追加日志 | `.claude/sessions/<id>.transcript.jsonl` | 审计/回放（user_prompt、tool_use、tool_result、usage、compacted、done、error、aborted，见 `tui/session-transcript.ts:29-55`） |
| **目录索引** | JSON（`proper-lockfile` 加锁） | `.claude/sessions/catalog.json` | pinned + preview 缓存（`session-memory.ts:240-269`） |

`src/persistence.ts` 只是 20 行的向后兼容壳：`PersistenceManager extends SessionMemory`（persistence.ts:20），真实逻辑在 `session-memory.ts`。

**快照 Schema（v3）**：`version/sessionId/createdAt/updatedAt/workspaceRoot/messages/messageCount/completed/taskState/lastTerminalReason`，其中 `taskState` 是运行时生命周期（`waiting_for_model | waiting_for_tool | recovering | paused | failed | stopped_by_user`，session-memory.ts:38-44）。v1→v2→v3 有顺序迁移函数（session-memory.ts:79-137），迁移失败降级为 null。

**写入路径的关键防护**（session-memory.ts:386-471）：
- `saveChain` Promise 链把并发 save（TUI onSave / loop 自动保存 / 退出清理）串行化，防止 read-modify-write 互相覆盖；
- 原子写：`<file>.<pid>.tmp` + rename（452-454 行）；
- `lastSaved` Map 缓存上次写入对象，避免每次 save 重新读盘解析整个会话（P2 优化，192 行）；
- catalog preview 只在首条用户消息变化时才写（461-465 行节流）；
- 损坏文件：`JSON.parse` 抛 SyntaxError → 返回 null，静默当作不存在（533 行）。

### 1.2 resume / fork / rewind

**resume** 有三条入口：
1. **启动时**：`--session=<id>` / `--resume` / `--continue`（取最近一条），在 `cli-session.ts:52-107` 解析；加载后经 `microCompactByTime()` 清理可压缩的旧工具结果再入内存（88-90 行）。
2. **会话中 `/resume <prefix>`**：`commands/resume.ts` → `createResumeSession()`（cli-session.ts:128-155）。用前缀匹配 `searchSessions`，**要求恰好一个匹配**（136 行 `matches.length !== 1` 即失败）；命中后原地替换共享 `messages` 数组（`messages.length = 0` + push，保持数组引用同一性，agent-loop 依赖它）并热切换 `session.id`。
3. **TUI 无参 `/resume`**：交互式 picker（resume.ts:11-13 注释）。

**fork/branch 是三个互不相同、名不副实的概念**：
- `--fork-session`（CLI 标志）：resume 时生成新 UUID，把旧消息写进新文件——唯一真正的"会话分叉"（cli-session.ts:90-96）。
- `/branch`（commands/branch.ts）：把当前消息快照存成新会话文件，但**不切换**当前会话；头部注释宣称 "The new branch is resumed immediately"（第 5-6 行），代码实际只打印 "Resume it with: /resume <id>"（31 行）——文档与实现矛盾。
- `/fork`（commands/fork.ts）：**根本不 fork 会话**，而是拼一段"最近 12 条消息摘要"的 prompt（recapOfMessages，18-36 行），经 `CommandResult.prompt` 通道注入 agent loop，让模型自己调 task 工具开一个 `general` 子代理去"探索另一条路线"。

**rewind**（commands/rewind.ts + checkpoint.ts）：
- 对话回退：按 user 消息切 turn 边界，`/rewind n` 截掉最后 n 个 user turn（rewind.ts:61-70，直接改 `messages.length`）。
- 文件回退：靠 **checkpoint.ts 的纯内存影子快照**。机制：
  - `beginUserTurn()`（checkpoint.ts:144-154）在每个用户 turn 开始时对所有已跟踪文件拍"边界快照"（`turnSnapshots`），并用 **WeakMap 把 turn 号直接打在 user Message 对象上**（152 行），rewind 时经 `turnOfMessage()` 反查——避免了 `/clear`、自动压缩、`/resume` 造成序号错位（这是设计亮点）。
  - Write/Edit/MultiEdit/Notebook 工具在写盘前调 `shadowBeforeWrite()`（168-179 行）记录文件的"会话前原始内容"（`originals`，null = 原本不存在）与首写 turn。
  - `restoreToTurn()`（197-288 行）：首写 turn ≥ 目标 → 还原原始内容（原本不存在则删除文件）；首写 turn < 目标 → 还原目标 turn 的边界快照。还原本身用 tmp+rename 原子写（229-239 行），并回刷 read-tracker 的 mtime（246 行），避免后续 Edit 被"文件已变"误拒；失败时保留全部 checkpoint 数据以便重试（256 行）。
  - 子代理的 sessionId 形如 `<parent>-agent-<ts>`（tools/extended/agent.ts:356），`bucketKey()` 用正则剥掉后缀（checkpoint.ts:58-60），使子代理的文件写入随父会话一起回滚。
  - 有 mtime 内容缓存 + 严格的失效协议（100-118 行，处理同一 mtime tick 内连续写的 CI 场景）；快照上限 `MAX_TURN_SNAPSHOTS = 100`（122 行），超出后旧 turn 只能"仅对话回退"。
- **两个诚实声明的边界**：Bash 改的文件不在跟踪网内（checkpoint.ts:26-27）；`/resume` 载入的历史消息没有 WeakMap tag，rewind 只回退对话不回退文件（rewind.ts:72-75 会明说）。

**change-tracker.ts**（88 行）与 checkpoint 是两套账：它只记"本会话改了哪些文件"（kind/edits/detail/updatedAt）供 `/diff` 展示，纯内存 Map；rewind 后由 `forgetChanges()` 同步销账（checkpoint.ts:262-266）。**read-tracker.ts** 是"先读后改"守卫：按 `sessionId\0path` 记读取时的 mtime，Edit 时 mtime 不匹配即拒绝（read-tracker.ts:34-57）——同样纯内存。

## 2. 记忆体系

三个模块分工清晰，构成"三层记忆"：

```
session-memory.ts  → 会话本体（消息快照，resume 用）——名字叫 memory 其实是持久化层
memory-extract.ts  → 项目级长期记忆（.claude/memories.jsonl，主会话召回）
agent-memory.ts    → 子代理类型级记忆（.claude/agent-memory/<type>/MEMORY.md）
```

### 2.1 memory-extract（项目级长期记忆）

- **存储**：`.claude/memories.jsonl`，追加式，一行一条 `{id, ts, source: heuristic|model|manual, text, tags}`（MemoryStore，memory-extract.ts:192-256）。读取容忍坏行（218-224 行）；append 前按规范化文本（小写、折叠空白）全量去重（235 行——每次 append 都重读整个文件）。
- **写入路径（4 条）**：
  1. `/memory extract [--model]`（commands/memory.ts:66-96）：启发式规则扫 user 消息中的"持久意图"行——英文 `^(remember|always|never|prefer|...)`、中文 `^(请记住|记住|以后|不要|...)`（memory-extract.ts:48-50，专门为 CJK 无 `\b` 写了独立正则，细节到位），加上"本会话改动文件清单"一条；`--model` 追加一次模型侧调用，要求返回 JSON 字符串数组，任何失败静默返回 []（125-185 行）。
  2. `/memory save <text>`（memory.ts:44-57）：手动存一条。
  3. **MemorySave 工具**（tools/extended/memory-save.ts）：模型自主写记忆，可选 `agent_type` 同时落到该子代理的 MEMORY.md。
  4. **会话退出自动抽取**（cli.ts:723-737、772-786）：启发式 pass 默认开（只保留 preference 标签，故意排除 files-changed 噪音，memory-extract.ts:262-265），模型 pass 需 `CCR_AUTO_MEMORY_EXTRACT=1`，`=0` 全关。
- **召回路径**：不是嵌进 system prompt，而是 **M36 预取**（cli.ts:227-234 + prefetch.ts）：模型开始流式输出时并发跑一个纯关键词重叠排序（含中文分词 + CJK 停用词表），把 top 记忆和 top 技能作为 `<system-reminder>` 附件注入**下一轮**。CLAUDE.md 才是常驻 system prompt（system-prompt.ts:280-281）；`/memory add` 写 CLAUDE.md，`/memory save` 写 jsonl，两者定位在 memory.ts:41-43 注释里区分得很清楚。

### 2.2 agent-memory（子代理类型记忆）

- 三个 scope：`user`/`project`/`local`，但 **user 和 project 解析到同一路径** `<ws>/.claude/agent-memory/<type>/MEMORY.md`（agent-memory.ts:47-53，头注释承认 user 是 "legacy alias of project"）；只有 local 独立（`agent-memory-local/`，可用 `CCR_AGENT_MEMORY_LOCAL_DIR` 重定向）。**没有真正的跨项目用户级记忆**。
- 安全：`assertSafeAgentType()` 白名单 slug + 解析后路径二次校验防穿越（31-37、59-68 行）。
- 注入：`buildSubagentSystemPrompt()`（subagents.ts:251-263）在类型声明了 `memory:` 时把 MEMORY.md 拼进子代理 system prompt；loader 通过 `setAgentMemoryLoader` 依赖注入解耦 fs（subagents.ts:272-285，task.ts:33 注册）。
- `appendAgentMemory()`（147-177 行）：读-合并-写，按行去重，且做了 **CRLF 归一化**（163-166 行注释：Windows 编辑器保存的 CRLF 会击穿按行去重导致同一教训无限累积——这是踩过坑的痕迹）。

### 2.3 三者关系小结

session-memory 管"这次对话"，memory-extract 管"这个项目跨会话的事实/偏好"，agent-memory 管"这类子代理跨会话的经验"。写入都有去重与 best-effort（永不 throw 进主流程）；召回分别走 resume、prefetch 关键词排序、system prompt 注入。

## 3. 子代理 / 团队 / 结构化任务

### 3.1 subagents.ts —— 类型注册表

- 内建 3 型：`code-explorer`（只读+bash，20 turns）、`code-reviewer`（只读，30 turns）、`general`（读写+mcp__*，20 turns），各带 `whenToUse` 供父代理选择（68-105 行）。
- `resolveSubagentTools()` 支持前缀通配 `mcp__*` / `mcp__github__*`（138-153 行）。
- **上下文保护**：`extractLastAssistantText()` 只把子代理最后一条有文本的 assistant 消息返回给父级，明确修掉了旧实现"拼接全部 text_delta 导致子代理碎碎念泄漏进父上下文"的 bug（189-213 行注释）。
- 核心工具经 `setCoreToolsForSubagents()` 启动期注入，打破 tools.ts→TaskTool→tools.ts 循环依赖（155-184 行）。
- Task 工具（tools/extended/task.ts）：信号量限并发（默认 3，`TASK_MAX_CONCURRENCY` 可调），fork 嵌套深度上限 1（MAX_FORK_DEPTH，防 task→task 无限递归）；子代理权限走 `createSubAgentApprover` 受限审批。

### 3.2 team.ts —— 有状态多代理协作

与一次性 Task 相反，Team 是**具名、跨消息存活**的代理集合：
- 状态：`teams: Map<sessionId, Map<agentId, TeamAgent>>`，每个 agent 自带 `messages[]`（agentLoop 原地 mutate 实现历史累积）、status、CancellationScope（81 行起，**纯内存，进程重启即失**）。
- 工具面（tools/breadth/team.ts）：`team_create` / `send_message` / `task_list` / `task_get` / `task_stop` / `team_delete`。
- `runAgentTurn()`（200-328 行）设计点：scope 从父信号 fork，父级 Ctrl+C 级联中止（219 行）；`task_stop` 硬取消（154-163 行）；后台模式的完成结果经 `pushTaskNotification` **推**回主循环而非轮询（M41，309-316 行）；完成时触发 `TeammateIdle` hook（317-325 行）；权限用受限 approver 防止子代理绕过 bash/write 审批（238 行 "P0 Security Fix"）。
- agent 角色复用 subagents 注册表（含磁盘自定义 agent），每 turn 上限 `role.maxTurns ?? 10`，自动压缩阈值 50k。

### 3.3 structured-tasks.ts —— 项目管理式任务列表

- `TaskCreate/TaskGet/TaskUpdate/TaskList` 四个模型工具（tools/extended/structured-task-tools.ts），支持 status 流转、owner、blocks/blockedBy 依赖、metadata 合并（null 删键）、`process.hrtime.bigint()` 时间戳。
- **纯内存** `Map<sessionId, Map<taskId, task>>`（26 行），taskId 是**进程级全局计数器**（28-33 行）——不落盘，重启/resume 后任务列表蒸发，而历史消息里还引用着旧 id。
- 注意命名冲突：team.ts 里也导出 `TaskListTool`/`TaskGetTool`（名为 `task_list`/`task_get`），与 structured-task-tools 的 `TaskList`/`TaskGet` 是**两套并行、名字极像的任务系统**（一套管团队代理状态，一套管工作项），对模型和用户都易混淆。

## 4. 扩展体系

### 4.1 斜杠命令注册表

- 组织方式：M18 拆分，一命令一文件（`src/commands/<name>.ts`，53 个文件），`registry.ts:63-114` 手工组装 **48 个内建命令**的 `COMMANDS` 数组；根级 `commands.ts` 是兼容壳 + `handleSlashCommand` 分发器。
- 契约（commands/types.ts）：`SlashCommand { name, description, run(args, ctx) }`；`CommandContext` 是一个约 25 个字段的巨型可选字段包（messages、persistence、resumeSession、mcpManager、hooks、goal/outputStyle/editorMode 等 `{value}` 可变 holder……）；`CommandResult.prompt` 通道（84-97 行）让 `/review`、`/fork`、磁盘命令统一走"注入 prompt 进 agent loop"。
- `/help` 通过 `bindCommandList` getter 动态合并内建 + 磁盘自定义命令（registry.ts:119）。

### 4.2 磁盘自定义命令 / skills / agents —— 三胞胎加载器

三个 loader 结构几乎复制粘贴（`loadCommandsDir.ts` / `skills/loadSkillsDir.ts` / `agents/loadAgentsDir.ts`）：扫 `<ws>/.claude/{commands,skills,agents}/`，解析 frontmatter，文件名安全校验（`/^[a-zA-Z0-9_-]+$/`），注册进各自 Map，项目级覆盖用户级。模板展开共用 `utils/disk-template.ts`：`$ARGUMENTS`、`$1..$9`、`${ENV}`、`` !`cmd` `` 壳执行（10s 超时）。

⚠️ **trustedShell 信任判定缺陷（严重，详见 §6.3）**：`loadCommandsDir.ts:141` 和 `loadSkillsDir.ts:134` 用 `index === 0` 决定 `` !`cmd` `` 是否可执行，默认环境下项目目录即 roots[0] → 项目级模板获得 shell 信任。

**skills 的独特设计**（skills.ts）：
- "发现便宜、加载贵"：目录只含 name/description/whenToUse，**发现预算 = 上下文窗口的 1%**（196-234 行，按 200k×1%×4 chars ≈ 8000 字符截断，溢出显示 "…and N more"）；完整 body 惰性到调用时才展开（`getPromptForCommand`）。
- 内建 4 个（deep-research/code-review/security-review/verify），三来源（builtin/disk/mcp）一注册表；用户的 `/<name>` 只是 Skill 工具的语法糖。
- `context: fork` 的 skill 不注入本对话，而是由 `skills/forkSkill.ts` 起一个子代理跑，可用 `allowedTools` 进一步收窄工具集（69-72 行），只回传最终文本。

### 4.3 plugins

- 清单 `plugin.json`：name/version(semver 强校验)/dependencies/skills/commands/agents/hooks/mcp/disabled；路径字段显式拒绝绝对路径与 `..` 段（plugins.ts:39-51）。
- **自带 180 行手写 ZIP 解压器**（extractZip，101-179 行）：防 zip-slip（路径逃逸即整包拒绝）、防解压炸弹（单条目 64MB 声明+实际双检、整包 256MB、2 万条目上限、`inflateRawSync maxOutputLength` 对付撒谎的 header）、拒绝 Zip64。安全工程相当认真。
- 安装：本地目录 cpSync / 远程 URL（zip 或裸 manifest+相对路径拉取，190-238 行）；marketplace 是 `.claude/marketplace.json` 单文件索引，`/plugin marketplace add <url>` 拉取合并；依赖检查只支持 `x.y.x` 通配（262 行）。
- 消费：`cli-tools.ts:59-76` 把每个启用插件目录再喂给三个 loader；MCP 会读插件目录下的 `mcp.json`（mcp/index.ts:897-902）。
- ⚠️ manifest 的 `skills/commands/agents/hooks` 路径字段经严格校验却**无人消费**（loader 固定拼 `.claude/` 子路径）；`hooks` 字段完全未接线。

### 4.4 加载时序（cli-tools.ts:37-108）

核心工具注册 → `setCoreToolsForSubagents` → 磁盘 skills → 插件目录（skills/commands/agents）→ 磁盘 commands → 磁盘 agents → MCP。全部 try/catch 包裹，"畸形扩展目录永不阻塞启动"。

## 5. 周边集成

- **git-context.ts**：两个用途。① `gatherGitContext()`（branch + 最多 20 条 porcelain 脏文件 + 5 条近期 commit，全部只读、3s 超时、任何失败返回 null）注入 system prompt 动态段，`/cd` 后重采（cli.ts:158-176）；② `gatherDiffSummary()` 为 `/commit`（vs HEAD，含 numstat 增删行数）和 `/pr`（vs upstream，含分支独有 commit）供料，外加一个纯启发式 conventional-commit 主题生成器 `suggestCommitSubject()`（249-275 行）。
- **lsp.ts / lsp-legacy.ts**：不是通用 LSP，是**手写的 tsserver JSON 协议客户端**（tsserver 不讲标准 LSP，Content-Length 有 +1 尾换行的怪癖在 1-15 行注释里写清了），零 npm 依赖。每工作区一个常驻进程（`getLspClient` 单例 + `disposeAllLspClients` 退出清理），提供：单文件 syntactic+semantic 诊断（`lsp_diagnostics` 工具）、光标补全 top50（`lsp_completions` 工具）、以及 `geterrForProject` 全项目诊断扫——这里对 tsserver "无成功响应帧、只靠 requestCompleted 事件收尾" 的协议怪癖处理得很细（236-350 行：事件门控防上一轮扫尾事件漏进下一轮、deadline 返回部分结果、服务器拒绝时**抛错**让工具回落到 `npx tsc --noEmit` 而非谎报干净）。lsp-legacy.ts 保留纯解析/格式化助手供 tsc 回落路径与旧测试使用。
- **telemetry.ts**：**纯本地、默认关闭**的 JSONL 事件记录（`.claude/telemetry/events.jsonl`），`CCR_TELEMETRY=1` 或 settings.json 显式开启。只记事件名与粗粒度元数据：`session_start`（provider/model/工具数/MCP 数/权限模式，cli.ts:138）、`turn`、`tool_results` 计数、`session_end`（cli-repl.ts:147/485/574）——不记 prompt/响应内容，永不联网，`record()` 永不 throw。
- **debug-logger.ts**：`DEBUG_STREAM=1|text|tools|all|off` 的 stderr 调试流（delta 预览截 50 字符），与 telemetry 是两套独立可观测通道。
- **tools/session-cwd.ts**：弥补"每次 Bash 全新 shell"的缺陷——只识别**裸 `cd <dir>`**（含引号；带 `;&|<>` 的复合命令一律不认，50-67 行），成功后记住目录作为下一次 spawn 的 cwd；目录消失自动清除陈旧条目（23-33 行）；后台任务的 cd 故意不记（79-81 行注释解释了竞态）；明确声明不做工作区围栏（Bash 本来就是无限制 shell）。

## 6. 弱点

### 6.1 数据一致性

1. **进程内串行 ≠ 跨进程安全**：`saveChain` 只保护单进程；会话 JSON 文件本身**没有文件锁**（只有 catalog.json 用了 proper-lockfile，session-memory.ts:255）。两个终端 resume 同一会话 = 后写者全胜，先写者的消息静默丢失。
2. **`save()` 注释与实现不符的隐患**：注释称 "Each link captures its own sessionId/messages snapshot"（391-392 行），实际捕获的是**数组引用**——链上排队的 save 执行时序列化的是那一刻的可变数组。`/rewind` 原地截断 messages 后若队列中还有旧 save，写入的是截断后的状态（此处侥幸无害，但语义与注释背离）。
3. **rewind 后的磁盘/内存窗口期**：`/rewind` 只改内存 messages，不触发 save（save 点在下一轮开始 cli-repl.ts:280 或退出 :152）。若 rewind 后进程被 kill，磁盘会话仍是未回退版本，而工作区文件已回退——两者不一致。
4. **损坏恢复是"静默重生"**：会话 JSON 解析失败直接返回 null（session-memory.ts:533），下次 save 会**用新文件覆盖损坏文件**，没有备份/告警（迁移失败至少有 warn，518 行）。transcript 和 memories.jsonl 的坏行容忍做得好，但快照文件坏 = 整个会话不可恢复。
5. **孤儿转录**：`deleteSession()` 只删 `<id>.json`（287-303 行），`<id>.transcript.jsonl` 永久残留。
6. **transcript seq 每进程从 0 重新计数**（session-transcript.ts:96-97），resume 后追加会产生重复 seq，破坏"单调序号"约定。
7. **checkpoint/read-tracker/change-tracker/team/structured-tasks 全部纯内存**：重启后 rewind 失去文件恢复能力（代码诚实声明了），团队、任务列表、先读后改状态直接蒸发。

### 6.2 目录约定混乱

- `~/.claude` 用户级目录**只存在于注释里**：loadAgentsDir.ts:5-6、loadSkillsDir.ts:4、loadCommandsDir.ts:5 的头注释都宣称扫描 `~/.claude/...`，代码实际只扫工作区 + `CCR_USER_*_DIR` 环境变量重定向（loadAgentsDir.ts:41-45 等），三个文件都 `import os` 却从未使用（loadAgentsDir.ts:31、loadCommandsDir.ts:31）。agent-memory 的 `user` scope 也解析到与 `project` 完全相同的路径（agent-memory.ts:47-53）。换个工作目录，所有"用户级"扩展和记忆全部消失。
- **插件清单字段是死配置**（见 §4.3）。
- 工作区 `.claude/` 下混居 12+ 种东西：sessions、memories.jsonl、agent-memory(-local)、plugins、marketplace.json、telemetry、worktrees、skills、commands、agents、settings.json、mcp.json——运行时产物（telemetry/worktrees/sessions）与版本化配置（settings/commands）无分层，gitignore 策略无从下手。

### 6.3 信任模型的实质性漏洞（文档 vs 代码）

`loadCommandsDir.ts:141` 和 `loadSkillsDir.ts:134` 都用 **`index === 0`** 决定 `trustedShell`。设计意图（两处头注释均写明）是"只有用户级模板可执行 `` !`cmd` ``，项目级 prompt-only"。但 `commandDirRoots/skillDirRoots` 只在 `CCR_USER_*_DIR` 设置时才把用户目录 unshift 到 0 位——**默认环境下 index 0 就是项目目录**，于是：
- 克隆一个含 `.claude/commands/evil.md`（内嵌 `` !`curl …|sh` ``）的仓库 → 用户敲 `/evil` 即执行任意 shell；
- 更糟：插件目录经 `loadSkillsDir(pluginDir)` 扫描时 roots[0] = 插件内目录 → **远程安装的插件 skill 自动获得 trustedShell**（且能展开 `${ENV}` 泄环境变量）。ZIP 解压防了 zip-slip 和炸弹，却没防住模板信任级别的错误赋值。这是全项目安全工程最认真与最疏漏两处的直接冲突。

### 6.4 重复实现

- 两套"任务"系统命名撞车（§3.3）；`TaskListTool` 同名导出在两个模块里指不同工具。
- 三个磁盘 loader 90% 同构（扫描/安全名/frontmatter/注册），未抽公共骨架。
- change-tracker 的账本与 checkpoint 的 `firstWriteTurn` 大量重叠，靠 `forgetChanges` 手工对账（checkpoint.ts:262-266）。
- 三份可观测存储：telemetry.jsonl、transcript.jsonl、SessionStats，字段各有 overlap（usage/turn/toolCalls）。
- "fork"语义三分裂（§1.2）。
- persistence.ts、lsp-legacy.ts、commands.ts 三个兼容壳属有意为之，但增加了导航成本。

### 6.5 对比真实 Claude Code 的缺失能力

- **无 parent-UUID JSONL 链**：transcript 头注释明说 "Deliberately NOT the reference's parent-UUID JSONL chain — no branching, no leaf selection"。因此没有真正的会话树、sidechain（子代理转录并入父文件）、checkpoint 落盘。
- **会话不跟用户走**：真实 CC 存 `~/.claude/projects/<slug>/`，在任何 cwd 都能列同一项目的历史；这里 sessions 锁死在当前工作区路径，`/cd` 之后旧会话即不可见（SessionMemory 实例绑定 workspaceRoot 构造）。
- rewind/checkpoint 不跨进程（真实 CC 的 file-history 快照落盘）。
- CLAUDE.md 只读工作区根一份：无 `~/.claude/CLAUDE.md` 用户级、无嵌套目录 CLAUDE.md、无 `@import` 语法（system-prompt.ts:280 单块注入）。
- `/memory add` 后需重启会话才生效（memory.ts:33 自己承认），真实 CC 即时重载。
- 团队/任务无持久化；无 SendMessage 式代理间自由通信（只有点对点 send_message 工具）。
- skill 的 `allowedTools` 只在 fork 模式生效，inline skill 不受工具限制；无插件命名空间（`plugin:skill`）。
- LSP 仅 TypeScript（无其他语言服务器适配层——不过真实 CC 本体也没有 LSP，这算超额实现）。

### 6.6 性能（大会话）

- **`listSessions()` 全量读盘解析**（session-memory.ts:541-577）：列出会话 = 打开并 `JSON.parse` 每一个会话文件；catalog.json 只缓存了 pinned/preview，**没缓存 meta**，`/sessions`、`--continue`、resume picker 在积累几百个大会话后会明显卡顿。`searchSessions` 对无 preview 缓存的条目再加载一遍（339 行）。
- **每轮全量重写快照**：save 无增量，长会话每 turn `JSON.stringify` 整个消息数组 + 写盘（446-454 行）。`lastSaved` 只省掉了读，没省写。真实 CC 的追加式 JSONL 每轮只写增量。
- `beginUserTurn` 每次提交对**所有**被跟踪文件 `statSync`（checkpoint.ts:148 + 100-112），mtime 缓存省了 read 但 stat 是 O(跟踪文件数)/每轮的热路径（注释自己承认，88-92 行）。
- `MemoryStore.append` 每次全量读 jsonl 建去重集（memory-extract.ts:235）；`appendAgentMemory` 每次全量读写 MEMORY.md。
- `extractMemoriesWithModel` 把转录粗暴 `slice(0, 12000)` **取头不取尾**（memory-extract.ts:138）——长会话里最有价值的近期对话恰好被切掉；且 assistant 消息用 `m.content ?? ""` 直拼（133 行），content 为块数组时会字符串化成垃圾。
- 快照内存驻留：checkpoint 的 originals+turnSnapshots 保存每个跟踪文件最多 101 份全文件内容副本，大文件多轮编辑的会话内存占用无上限约束（只有 turn 数上限）。

## 7. 可升级点（按优先级）

1. **【安全·P0】修复 trustedShell 赋值**：`loadCommandsDir.ts:141`、`loadSkillsDir.ts:134` 把 `index === 0` 改为显式判断"该 root 是否来自 `CCR_USER_*_DIR`"（如让 `commandDirRoots/skillDirRoots` 返回 `{path, trusted}` 对象）。同时对插件目录扫描硬编码 `trustedShell: false`，或引入安装时用户确认。
2. **【一致性·P0】会话文件跨进程写保护**：把 catalog 已用的 `proper-lockfile`（session-memory.ts:255-258）推广到 `saveSerialized` 的 tmp+rename 段；或检测 mtime 前进 + 内容分歧时拒绝覆盖并提示。
3. **【性能·P1】catalog.json 升级为完整索引**：`listSessions()`（session-memory.ts:541-577）改为读 catalog 的 meta（sessionId/updatedAt/messageCount/taskState/preview），仅在文件 mtime 新于索引时回源重解析；顺手把 `deleteSession`（:287）补上删除 `.transcript.jsonl`。
4. **【能力·P1】checkpoint 落盘**：将 `originals`/`turnSnapshots` 持久化到 `.claude/checkpoints/<sessionId>/`（内容寻址去重可控制体积），使 rewind 跨重启、跨 resume 可恢复文件——补上 rewind.ts:72-75 那个"诚实的缺口"。
5. **【能力·P1】真正的用户级目录**：兑现三个 loader 头注释的 `~/.claude/{agents,skills,commands}` 承诺（用上那个已 import 未使用的 `os`，loadAgentsDir.ts:31），agent-memory 的 user scope 同理与 project 分离（agent-memory.ts:47-53）。

7. **【插件·P2】尊重 manifest 组件路径**：cli-tools.ts:59-76 改为按 `manifest.skills/commands/agents` 声明的路径装载，并把 `hooks` 字段接进 HookRegistry（当前完全未消费）；`mcp` 字段与 mcp/index.ts:897 的 `mcp.json` 约定二选一统一。
8. **【语义·P2】统一 fork/branch**：`/branch` 实现其注释宣称的"立即切换"（调用 `createResumeSession` 的换 id 逻辑，cli-session.ts:128），或改注释；`/fork` 可升级为 `--fork-session` 的会话内等价物（generateId + 复制消息 + 热切换），prompt 注入版本保留为 `/fork explore`。
9. **【记忆·P2】修 `extractMemoriesWithModel` 的窗口**：memory-extract.ts:130-138 改为取**尾部** 12k 字符（或头 2k+尾 10k），并用块感知的文本提取（同文件 `userText()` 的做法）处理 assistant content；`MemoryStore` 增加进程内去重集缓存避免每次全量读（:235）。

## 总评

这是一个工程素养明显高于平均水平的复刻——原子写、save 链、WeakMap turn 标记、zip 炸弹防护、CRLF 去重、tsserver 协议怪癖处理等细节都体现出对失败模式的认真思考，注释密度和"设计意图 vs 已知边界"的坦诚（如 Bash 不跟踪、resume 后文件不回退）尤其可贵。主要短板集中在三处系统性问题：**默认环境下项目级模板获得 shell 信任**（与其自身文档矛盾的安全缺陷）、**几乎所有运行时状态（checkpoint/team/tasks/read-tracker）不落盘导致重启即失忆**、以及**用户级目录约定只写在注释里未实现**。这三点修完，持久化与扩展体系可以称得上对真实 Claude Code 的高保真替代。
